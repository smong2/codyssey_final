# 장소 기반 스토리 규칙 — 시스템·백엔드용

> **문서 상태:** 시스템 설계 기준안  
> **현재 제작 범위:** [`LOCATION_STORY_PRODUCTION.md`](LOCATION_STORY_PRODUCTION.md)  
> **과거 전체 시나리오 검토표:** [`feedback_장소기반.md`](feedback_장소기반.md)  
> **목적:** Location Story의 발생 확률, 순서, 주간 제한, 상태 저장 및 백엔드 판정 규칙을 정의한다.  
> **주의:** 본편 시나리오 내용·대사 제작 기준은 `LOCATION_STORY_PRODUCTION.md`와 별도 대화 데이터에서 관리한다. `feedback_장소기반.md`는 과거 전체안과 노출 시점 참조용이다.

---

## 1. 핵심 정의

Location Story는 특정 장소를 방문했을 때 조건을 만족하면 랜덤하게 발생하는 장소 전용 시나리오다.

본편에서 활성화하는 Location Story는 제작 범위 축소 결정에 따라 다음 **6개만** 사용한다.

```text
LOC_OBS_01 → LOC_OBS_02 → LOC_OBS_03 → LOC_OBS_04
LOC_GH_01
LOC_LIB_01
```

`LOC_GH_02`, `LOC_LIB_02`, `LOC_WRK_01~02`, `LOC_TRN_01~02`, `LOC_CLK_01~02`, `LOC_DRM_01~02`는 본편 제작·발생 후보에서 제외한다. 과거 문서에 남아 있더라도 런타임 후보로 등록하지 않는다.

핵심 원칙은 다음 한 문장으로 정리한다.

> **무슨 이야기가 나올지가 랜덤한 것이 아니라, 장소별로 정해진 다음 이야기가 언제 발생할지가 랜덤하다.**

천문대와 다른 장소는 같은 실행 로직을 사용한다. 장소마다 시나리오 개수와 내용만 다르다.

### 1.1 수업·특수 활동과의 실행 순서

WBS 2.4의 7개 공간 콘텐츠는 Location Story와 별도 계층이다. 수업 미니게임이나 기숙사 `요정의 거래`를 위해 장소를 방문했다면 **예약된 활동을 먼저 끝내고 결과를 확정한 뒤** Location Story를 판정한다.

```text
공간 활동 진입
→ 미니게임 / 요정의 거래
→ 정상 결과 확정·저장
→ Location Story 후보 판정
→ 발생 시 별도 이벤트
→ 다음 일정
```

- Location Story가 수업 미니게임이나 요정의 거래를 대신하지 않는다.
- 미니게임·요정의 거래·직접 모험 플레이 내부에는 NPC 대화나 이야기 장면을 겹쳐 실행하지 않는다. Location Story는 정상 활동 결과 저장 뒤 분리된 이야기 장면에서만 시작한다.
- 미니게임이 `FAIL` 또는 사용자의 `포기하기`로 정상 종료되어도 활동 결과가 확정되었다면 이후 Location Story 판정은 가능하다.
- 미니게임 도중 비정상 종료되어 `INTERRUPTED` 복구된 방문에서는 Location Story를 새로 판정하지 않는다.
- Location Story는 기존 규칙대로 일반 일정 슬롯을 추가 소비하지 않는다.
- 메인 스토리 강제 방문은 아래 5장의 기존 예외 규칙을 우선한다.

## 2. 기본 발생 규칙

### 2.1 장소별 sequence 고정

- 각 장소의 시나리오는 `sequence` 순서대로 진행한다.
- 이전 sequence가 해결되지 않았다면 다음 sequence는 발생하지 않는다.
- 활성 시나리오 ID와 제작 범위는 `LOCATION_STORY_PRODUCTION.md`를 우선한다. 기존 노출 시작일·주차가 필요한 경우 활성 6개에 한해서 `feedback_장소기반.md`의 기존 값을 참조하며, 제외된 ID를 다시 활성화하는 근거로 사용하지 않는다.

예:

```text
LOC_OBS_01 → LOC_OBS_02 → LOC_OBS_03 → LOC_OBS_04
LOC_GH_01
LOC_LIB_01
```

### 2.2 노출 시작일

- 각 Location Story에는 `unlock_date`와 대응하는 `unlock_week`가 있다.
- `unlock_date` 이전에는 절대 발생하지 않는다.
- `unlock_date`는 발생 확정일이 아니라 최초 발생 가능일이다.
- 달력 기준은 `1월 1일 = 월요일`, 비윤년이다.

### 2.3 다음 sequence의 실제 활성화 시점

두 번째 이후 시나리오는 원래의 `unlock_week`가 지났더라도 이전 sequence가 해결되어야 한다.

다음 sequence의 실제 확률 계산 시작점은 다음과 같이 계산한다.

```text
effective_unlock_week
= max(configured_unlock_week, previous_resolved_week + 1)
```

예:

```text
LOC_OBS_02 configured_unlock_week = 22
LOC_OBS_01 resolved_week = 28

→ effective_unlock_week = 29
```

이 규칙으로 이전 이야기가 늦게 끝났을 때 다음 이야기가 즉시 고확률로 연속 발생하는 것을 막는다.

## 3. 발생 확률

`effective_unlock_week`부터 시간이 지날수록 발생 확률이 상승한다.

| 경과 주차 | 발생 확률 |
|---:|---:|
| 0주 | 20% |
| 1주 | 30% |
| 2주 | 40% |
| 3주 | 50% |
| 4주 | 60% |
| 5주 | 70% |
| 6주 | 80% |
| 7주 | 90% |
| 8주 이상 | 100% |

계산식:

```text
elapsed_weeks = current_week - effective_unlock_week

if elapsed_weeks >= 8:
    probability = 100
else:
    probability = 20 + (elapsed_weeks * 10)
```

### 중요

- 확률은 해당 장소를 실제 방문했을 때만 판정한다.
- 장소를 방문하지 않았다고 자동으로 이벤트가 발생하지 않는다.
- 8주가 지나 100%가 되어도 다음 해당 장소 방문 전까지는 발생하지 않는다.

## 4. 주간 판정 제한

### 4.1 같은 후보는 한 주 1회만 판정

같은 장소를 한 주에 여러 번 방문해 확률을 반복해서 굴릴 수 없다.

```text
월요일 온실 방문
→ LOC_GH_01 판정 실패

수요일 온실 재방문
→ 재판정하지 않음

다음 주 온실 방문
→ 다시 판정 가능
```

이를 위해 각 후보별 `last_roll_week`를 저장한다.

### 4.2 전체 Location Story는 한 주 최대 1회 발생

- 여러 장소가 동시에 후보 상태일 수 있다.
- 아직 그 주에 실제 Location Story가 발생하지 않았다면 다른 장소 방문에서 각각 판정할 수 있다.
- 어느 장소에서든 하나가 성공해 실제 시나리오가 발생하면 그 주에는 다른 Location Story를 더 이상 판정하지 않는다.

예:

```text
월요일 대서고 방문
→ LIB 후보 판정 실패

화요일 온실 방문
→ GH 후보 판정 성공
→ Location Story 발생

수요일 시계탑 방문
→ 이번 주에는 Location Story 판정 안 함
```

회차 주간 상태에는 최소 다음 값을 둔다.

```text
location_story_triggered_week
```

현재 주차와 값이 같으면 추가 Location Story 판정을 막는다.

## 5. 메인 스토리와의 관계

Location Story와 Main Story는 별도 콘텐츠 계층으로 본다.

규칙:

1. 현재 장소 방문 자체가 메인 스토리 장면을 실행하기 위한 방문이면 같은 방문에서는 Location Story를 판정하지 않는다.
2. 메인 스토리가 발생한 주라고 해서 그 주의 Location Story 전체를 막지는 않는다.
3. Location Story는 메인 스토리 핵심 정보 전달 수단으로 사용하지 않는다.
4. 메인 스토리보다 먼저 또는 나중에 발생해도 시간축 모순이 없어야 한다.

예:

```text
3월 5일 온실에서 MS02 메인 스토리 진행
→ 같은 방문의 LOC_GH_01 판정 없음

같은 주 다른 날 대서고 방문
→ 그 주 Location Story가 아직 발생하지 않았다면 LOC_LIB_01 정상 판정 가능
```

## 6. 장면 결과

Location Story가 노출되면 플레이어가 행동하거나 지나갈 수 있다.

기본 결과값:

```text
ACTION = 행동함
SKIP   = 행동하지 않고 지나감
```

현재 제작하는 6개 장면은 모두 장면 내부에 **플레이어 대사 선택 1회 이상**을 가진다. 이 선택은 `choice_code`로 기록하는 장면 내부 선택이며 `ACTION / SKIP`과는 별도다.

- 장면을 정상적으로 읽고 선택 대사를 고른 뒤 끝내면 `resolution=ACTION`으로 처리한다.
- `SKIP`은 게임 UI가 **이 Location Story 전체를 보지 않고 지나가는 기능**을 제공할 때만 사용한다.
- 선택지의 어느 항목을 골랐는지를 `SKIP`으로 해석하지 않는다.
- `SKIP` UI를 제출판에서 제공하지 않으면 활성 6개 장면의 정상 완료 결과는 `ACTION`만 사용해도 된다.

원칙:

- `ACTION`, `SKIP` 모두 해당 sequence는 해결된 것으로 처리할 수 있다.
- `SKIP`을 실패나 불이익으로 처리하지 않는다.
- `SKIP` 때문에 다음 sequence가 영구적으로 막히지 않는다.
- 환경 변화와 후속 반응은 필요하면 `ACTION`에만 적용한다.
- 실제 선택 문구와 대사는 별도 데이터에서 정의한다.

## 7. 환경 변화와 후속 반응

원본 시나리오에 있는 `다음 방문에서 보이는 작은 변화`는 별도의 Location Story로 만들지 않는다.

예:

```text
LOC_GH_01 결과 = ACTION
→ environment_state_key = GH_HERB_WATERED

다음 온실 방문
→ GH_HERB_WATERED 상태 확인
→ 물방울 표현 또는 짧은 반응 출력
```

따라서 다음 방문 반응은 **새 sequence가 아니라 장소 상태 표현**이다.

환경 변화는 반드시 별도 이미지로 만들 필요가 없다. 필요에 따라 다음 중 하나를 사용할 수 있다.

- 기존 오브젝트 상태 변경
- 짧은 텍스트 반응
- NPC 한 줄 반응
- 작은 UI 표시

## 8. 한 회차 내 반복 규칙

- 같은 Location Story는 같은 회차에서 다시 발생하지 않는다.
- 해당 장소의 모든 sequence가 끝나면 이후 방문은 일반 장소 반응만 사용한다.
- Location Story 전체 진행도를 회차마다 초기화할지 계정에 유지할지는 아직 별도 확정이 필요하다.

## 9. 백엔드 판정 순서

장소 진입 시 다음 순서로 처리한다.

```text
1. 현재 방문이 메인 스토리 강제 장면인가?
   YES → Location Story 판정 종료
   NO  → 계속

2. 이번 주에 이미 Location Story가 실제 발생했는가?
   YES → 판정 종료
   NO  → 계속

3. 현재 장소에 미해결 sequence가 남아 있는가?
   NO  → 판정 종료
   YES → 가장 낮은 미해결 sequence를 후보로 선택

4. previous_story_id 조건을 만족했는가?
   NO  → 판정 종료
   YES → 계속

5. effective_unlock_week 계산

6. current_week >= effective_unlock_week 인가?
   NO  → 판정 종료
   YES → 계속

7. candidate.last_roll_week == current_week 인가?
   YES → 판정 종료
   NO  → 계속

8. 경과 주차 기반 probability 계산

9. RNG 판정
   실패:
     - last_roll_week = current_week
     - 일반 장소 진행

   성공:
     - last_roll_week = current_week
     - location_story_triggered_week = current_week
     - Location Story 실행

10. 장면 종료 시 resolution 저장
    - ACTION 또는 SKIP
    - resolved_week = current_week
    - status = RESOLVED

11. 필요한 경우 environment_state 적용
```

## 10. 마스터 데이터 필드 제안

실제 테이블명과 정규화 수준은 백엔드에서 결정하되, 최소한 다음 값을 관리한다.

| 필드 | 예시 | 의미 |
|---|---|---|
| `story_id` | `LOC_GH_01` | Location Story 고유 ID |
| `location_code` | `GH` | 발생 장소 |
| `sequence` | `1` | 장소 내부 순서 |
| `title` | `작은 허브에 물 주기` | 시나리오명 |
| `unlock_date` | `02-12` | 최초 발생 가능 날짜 |
| `unlock_week` | `7` | 최초 발생 가능 주차 |
| `base_probability` | `20` | 시작 확률(%) |
| `weekly_probability_increment` | `10` | 매 경과 주 증가(%p) |
| `guarantee_after_weeks` | `8` | 100% 도달 경과 주차 |
| `previous_story_id` | `null` / `LOC_GH_01` | 선행 시나리오 |
| `dialogue_set_id` | 별도 값 | 대화 데이터 연결 |
| `environment_state_key` | 별도 값 | 환경 변화 연결 |
| `is_active` | `true` | 사용 여부 |

활성 시나리오의 실제 `story_id`, `location_code`, `sequence`, `title`과 제작 여부는 `LOCATION_STORY_PRODUCTION.md`를 우선한다. `unlock_date`, `unlock_week`는 활성 6개에 한해 기존 `feedback_장소기반.md` 값을 참조하되, 제작본에서 별도 확정되면 제작본 값을 우선한다.

## 11. 회차별 진행 데이터 필드 제안

| 필드 | 예시 | 의미 |
|---|---|---|
| `run_id` | 현재 회차 ID | 회차 구분 |
| `story_id` | `LOC_GH_01` | 대상 이벤트 |
| `status` | `LOCKED / ELIGIBLE / RESOLVED` | 진행 상태 |
| `effective_unlock_week` | `7` | 실제 확률 계산 시작 주차 |
| `last_roll_week` | `9` | 같은 주 재판정 방지 |
| `resolved_week` | `11` | 해결 주차 |
| `resolution` | `ACTION / SKIP` | 결과 |
| `choice_code` | 선택값 | 세부 선택 결과 |
| `state_applied` | `true/false` | 환경 상태 적용 여부 |

`effective_unlock_week`는 저장하지 않고 매번 계산할 수도 있다. 실제 저장 여부는 백엔드 구현 방식에 따라 결정한다.

## 12. 천문대와 다른 장소를 같은 로직으로 처리

기존 시나리오 문서는 천문대를 연속 이야기, 다른 장소를 생활 이벤트로 구분했지만 실행 시스템에서는 구분하지 않는다. 현재 활성 범위는 천문대 4회와 온실·대서고 각 1회다.

| 시스템 조건 | 천문대 | 온실·대서고 |
|---|---|---|
| 장소 방문 시 후보 판정 | O | O |
| sequence 순서 | O | O |
| unlock_date | O | O |
| 확률 증가 | O | O |
| 주간 판정 제한 | O | O |
| 한 주 전체 1회 제한 | O | O |
| 결과 저장 | O | O |

천문대는 `sequence = 1~4`, 온실·대서고는 현재 각 `sequence = 1`만 활성화한다.

## 13. 아직 확정이 필요한 시스템 항목

다음은 별도 결정이 필요하다.

- Location Story 진행도를 회차마다 초기화할지 계정 단위로 유지할지
- Location Story와 NPC 개별 스토리가 같은 방문에서 동시에 조건을 만족했을 때 우선순위
- Location Story 결과를 보이지 않는 스탯 또는 엔딩 판정에 직접 반영할지
- 기념품·수집품 보상을 시스템적으로 연결할지
- 실제 RNG 구현 방식과 seed 사용 여부
