# 장소 기반 스토리 규칙 — 시스템·백엔드용

> **문서 상태:** 시스템 설계 기준안  
> **현재 제작 범위:** [`LOCATION_STORY_PRODUCTION.md`](LOCATION_STORY_PRODUCTION.md)  
> **과거 전체 시나리오 검토표:** [`feedback_장소기반.md`](feedback_장소기반.md)  
> **목적:** Location Story의 후보 조건, 순서, 공통 주간·일일 제한, 상태 저장 및 백엔드 판정 규칙을 정의한다.  
> **주의:** 본편 시나리오 내용·대사 제작 기준은 `LOCATION_STORY_PRODUCTION.md`와 별도 대화 데이터에서 관리한다. `feedback_장소기반.md`는 과거 전체안과 노출 시점 참조용이다.

---

## 1. 핵심 정의

Location Story는 특정 장소의 일반 활동을 시작할 때 서버가 시작 체크포인트를 먼저 저장한 뒤, 실제 미니게임·모험·특수 활동 화면을 노출하기 **직전** 조건을 만족하면 별도 이야기 장면으로 선정될 수 있는 장소 전용 시나리오다.

본편에서 활성화하는 Location Story는 제작 범위 축소 결정에 따라 다음 **6개만** 사용한다.

```text
LOC_OBS_01 → LOC_OBS_02 → LOC_OBS_03 → LOC_OBS_04
LOC_GH_01
LOC_LIB_01
```

`LOC_GH_02`, `LOC_LIB_02`, `LOC_WRK_01~02`, `LOC_TRN_01~02`, `LOC_CLK_01~02`, `LOC_DRM_01~02`는 본편 제작·발생 후보에서 제외한다. 과거 문서에 남아 있더라도 런타임 후보로 등록하지 않는다.

핵심 원칙은 다음 한 문장으로 정리한다.

> **현재 본편은 Location 전용 고정 확률을 사용하지 않는다. 장소별 다음 이야기는 earliestWeek·선행 완료·공통 발생 제한을 만족하는 방문에서 eligible 후보가 된다.**

천문대와 다른 장소는 같은 실행 로직을 사용한다. 장소마다 시나리오 개수와 내용만 다르다.

### 1.1 수업·특수 활동과의 실행 순서

WBS 2.4의 7개 공간 콘텐츠는 Location Story와 별도 계층이다. 장소 방문에서 Location Story가 발생한다면 **활동 시작 체크포인트를 저장한 뒤 실제 플레이 화면을 띄우기 전에** Story를 먼저 실행하고, Story 완료 저장 성공 뒤 원래 활동을 이어서 시작한다.

```text
공간 활동 진입
→ 활동 시작 체크포인트(IN_PROGRESS) 저장
→ Location Story 후보 판정
→ 발생 시 별도 이벤트 먼저 실행·완료 저장
→ 미니게임 / 요정의 거래 / 모험 실행
→ 정상 결과 확정·저장
→ NPC Story 후보 판정
→ 다음 일정
```

- Location Story가 수업 미니게임이나 요정의 거래를 대신하지 않는다. Story가 끝나면 같은 `IN_PROGRESS` 활동을 그대로 시작한다.
- 미니게임·요정의 거래·직접 모험 플레이 내부에는 NPC 대화나 이야기 장면을 겹쳐 실행하지 않는다. Location Story는 플레이 화면 **직전**, NPC Story는 정상 활동 결과 저장 **뒤**의 분리된 이야기 장면에서만 시작한다.
- Location Story가 이미 완료된 뒤 활동 도중 비정상 종료되어도 같은 방문에서 Location을 다시 선정하지 않는다. `pendingStoryEvent`가 남았다면 그 Story를 먼저 복구한다.
- Location Story는 기존 규칙대로 일반 일정 슬롯을 추가 소비하지 않는다.
- 메인 스토리 강제 방문은 아래 5장의 기존 예외 규칙을 우선한다.

## 2. 기본 발생 규칙

### 2.1 장소별 sequence 고정

- 각 장소의 시나리오는 `sequence` 순서대로 진행한다.
- 이전 sequence가 해결되지 않았다면 다음 sequence는 발생하지 않는다.
- 활성 시나리오 ID와 제작 범위는 `LOCATION_STORY_PRODUCTION.md`를 우선한다. 기존 노출 시작일·주차가 필요한 경우 활성 6개에 한해서 `feedback_장소기반.md`의 기존 값을 참조하며, 제외된 ID를 다시 활성화하는 근거로 사용하지 않는다.

예:

```text
LOC_OBS_01 → LOC_OBS_02 → LOC_OBS_03 → LOC_OBS_04
LOC_GH_01
LOC_LIB_01
```

### 2.2 노출 시작 주차

- 각 Location Story에는 최초 후보 가능 주차 `earliest_week`가 있다.
- 활성 6개는 기존 기간 분배 결정을 복원해 `OBS01=3`, `GH01=7`, `LIB01=13`, `OBS02=22`, `OBS03=33`, `OBS04=46`을 사용한다.
- 기준일은 각각 `1/15, 2/12, 3/26, 5/28, 8/13, 11/12`다.
- `earliest_week`는 발생 확정 주차가 아니라 최초 후보 가능 주차다.

### 2.3 다음 sequence의 활성 조건

천문대 두 번째 이후 이야기는 자신의 `earliest_week`를 넘었더라도 바로 후보가 되지 않는다. 직전 Location Story가 `COMPLETED`여야 한다.

```text
LOC_OBS_02 requires LOC_OBS_01 COMPLETE
LOC_OBS_03 requires LOC_OBS_02 COMPLETE
LOC_OBS_04 requires LOC_OBS_03 COMPLETE
```

직전 이야기가 늦게 끝났다면 다음 이야기는 그 완료 이후의 **다음 정상 후보 판정 시점**부터 조건을 검사한다. 별도의 `effective_unlock_week`나 누적 확률 값은 저장하지 않는다.

## 3. 후보 선정 정책

현재 본편 Location Story는 별도 `20% → 100%` 고정 확률을 사용하지 않는다. 최신 공통 이벤트 규칙과 SQLite v4의 `story_event_rules.selection_policy = UNSEEN_FIRST`를 따른다.

활동 시작 체크포인트 저장 뒤 실제 플레이 화면을 노출하기 전에 현재 장소에서 다음 조건을 모두 만족한 Story만 eligible 후보가 된다.

1. `story_event_rules.is_active = 1`
2. `trigger_phase = AFTER_ACTIVITY`
3. 현재 활동 장소와 `stories.location_id` 일치
4. `current_week >= story_steps.earliest_week`
5. `storyProgress[storyId]`가 `COMPLETED`가 아님
6. `PREVIOUS_EVENT_COMPLETE` 등 추가 condition 충족
7. 같은 날/주 `SIDE_STORY` 공통 제한을 초과하지 않음
8. 해당 주 `locationStoryCount < 1`
9. 현재 `pendingStoryEvent`가 없음

조건을 만족한 현재 장소의 Location Story 중 **아직 완료하지 않은 Story를 우선**한다. 천문대는 선행 완료 조건 때문에 실제로 한 번에 다음 장면 하나만 eligible이 된다.

장소를 방문하지 않았다고 자동으로 Location Story가 실행되지는 않는다. 또한 메인 강제 방문처럼 Location 후보 판정을 금지한 흐름에서는 후보를 만들지 않는다.

## 4. 주간 판정 제한

### 4.1 확률 재판정 상태를 저장하지 않음

현재 Location은 별도 RNG roll을 사용하지 않으므로 `last_roll_week`, `effective_unlock_week`, 장소별 누적 확률을 저장하지 않는다. 해당 방문에서 공통 제한 때문에 실행하지 못했거나 eligible 후보가 없었다면 다음 정상 장소 방문에서 다시 현재 조건을 계산한다.

### 4.2 NPC + Location Story 공통 제한

- NPC Story + Location Story 합계 **주당 최대 2회**
- Location Story 자체는 **주당 최대 1회**
- 결과를 가지는 Story는 **하루 최대 1회**
- Main Story는 이 제한에 포함하지 않음
- Story가 선정되어 `pendingStoryEvent`가 남아 있으면 새 후보를 선정하지 않음

Firestore `activeRun.storyEventWindow`의 최소 상태:

```text
week
sideStoryCount
locationStoryCount
lastResultStoryDay
```

새 주가 시작되면 이 주간 창을 초기화한다.

## 5. 메인 스토리와의 관계

Location Story와 Main Story는 별도 콘텐츠 계층으로 본다.

규칙:

1. 현재 장소 방문 자체가 메인 스토리 장면을 실행하기 위한 방문이면 같은 방문에서는 Location Story를 판정하지 않는다.
2. 메인 스토리가 발생한 주라고 해서 그 주의 Location Story 전체를 막지는 않는다.
3. Location Story는 메인 스토리 핵심 정보 전달 수단으로 사용하지 않는다.
4. 메인 스토리보다 먼저 또는 나중에 발생해도 시간축 모순이 없어야 한다.

예:

```text
3월 5일 온실에서 MS02 메인 스토리 진행
→ 같은 방문의 LOC_GH_01 판정 없음

같은 주 다른 날 대서고 방문
→ 그 주 Location Story가 아직 발생하지 않았다면 LOC_LIB_01 정상 판정 가능
```

## 6. 장면 결과

현재 공통 Dialogue 계약을 그대로 사용한다.

```text
COMPLETE = 실제 대화를 끝까지 진행하고 필요한 선택을 완료
SKIP     = 서버가 canSkip=true로 허용한 상태에서 대화 전체를 스킵
```

현재 제작하는 6개 장면은 모두 장면 내부에 **플레이어 대사 선택 1회 이상**을 가진다. 정상 `COMPLETE`에서는 선택한 canonical `choiceId`를 서버가 검증해 `story_choice_effects`를 적용한다.

`SKIP`은 일반적인 “행동하지 않고 지나가기” 선택지가 아니다. 계정 첫 엔딩 이후 또는 QA 정책으로 허용되는 **Dialogue 전체 스킵**이다.

원칙:

- `COMPLETE`, `SKIP` 모두 해당 Location Story는 완료 처리하고 다시 발생시키지 않는다.
- `SKIP`에서는 보이는/보이지 않는 스탯과 선택 전용 event flag를 적용하지 않는다.
- `story_event_effects`의 `COMPLETE_OR_SKIP` 진행 효과는 두 경우 모두 적용한다.
- 천문대 다음 sequence의 선행 완료 조건은 SKIP 완료도 충족한다.
- 실제 선택 문구와 branch reaction은 `document/dialogue/location/`과 최종 32인 Character Set에서 정의한다.

## 7. 환경 변화와 후속 반응

원본 시나리오에 있는 `다음 방문에서 보이는 작은 변화`는 별도의 Location Story로 만들지 않는다.

예:

```text
LOC_OBS_04 COMPLETE + STAR 선택
→ eventFlags["location.obs.mark"] = "STAR"
```

현재 활성 6장면에서 별도 다음 방문 환경 상태가 반드시 필요한 것은 아니다. 온실은 같은 장면 안에서 `ART-L02 → ART-L03`로 회복을 확인하고, 대서고는 `ART-L04`를 숨기며 장면 안에서 정리를 완료한다. 천문대 마지막 선택처럼 후속 표시가 필요한 최소 값만 `eventFlags`에 저장한다.

환경 변화는 반드시 별도 이미지로 만들 필요가 없다. 필요에 따라 다음 중 하나를 사용할 수 있다.

- 기존 오브젝트 상태 변경
- 짧은 텍스트 반응
- NPC 한 줄 반응
- 작은 UI 표시

## 8. 한 회차 내 반복 규칙

- 같은 Location Story는 같은 회차에서 다시 발생하지 않는다.
- 해당 장소의 모든 sequence가 끝나면 이후 방문은 일반 장소 반응만 사용한다.
- Location Story 진행도는 `activeRun.storyProgress`에 저장하며 **새 회차 시작 시 초기화**한다. 계정 전역 영구 해금/메타로 유지하지 않는다.

## 9. 백엔드 판정 순서

일반 활동의 시작 체크포인트 저장 뒤 실제 게임 화면을 노출하기 전에 Location Story 후보 판정이 허용된 경우 다음 순서로 처리한다.

```text
1. 현재 방문이 메인 스토리 강제 장면인가?
   YES → Location Story 판정 종료
   NO  → 계속

2. pendingStoryEvent가 이미 있는가?
   YES → 새 후보 선정 종료, 기존 pending Story 우선
   NO  → 계속

3. SIDE_STORY 주간/일일 제한 또는 Location 주 1회 제한을 초과했는가?
   YES → 판정 종료
   NO  → 계속

4. 현재 장소와 location_id가 같은 활성 Location Story 조회

5. current_week >= earliest_week 인가?
   NO  → 후보 제외

6. storyProgress가 이미 COMPLETED인가?
   YES → 후보 제외

7. PREVIOUS_EVENT_COMPLETE 등 추가 condition을 만족하는가?
   NO  → 후보 제외

8. eligible 후보 중 UNSEEN_FIRST 정책으로 대상 확정
   후보 없음 → 일반 장소 진행
   후보 있음 → pendingStoryEvent 안정 저장 후 Location Story 실행

9. 장면 END/SKIP 완료 트랜잭션
    - 선택 효과(COMPLETE만) 적용
    - storyProgress = COMPLETED
    - storyEventWindow 갱신
    - pendingStoryEvent = null
    - phase = ACTIVITY_IN_PROGRESS로 복귀

10. 필요한 경우 environment/event flag 적용
```

## 10. 마스터 데이터 필드

SQLite v4의 실제 정규화 구조를 사용한다. Location 전용 별도 테이블을 만들지 않는다.

| 테이블/필드 | 예시 | 의미 |
|---|---|---|
| `stories.story_id` | `LOC_GH_01` | canonical Location Story ID |
| `stories.story_type` | `LOCATION` | Story 종류 |
| `stories.location_id` | `GH` | 발생 장소 |
| `story_steps.earliest_week` | `3 / 7 / 13 / 22 / 33 / 46` | Location별 최초 후보 가능 주차 |
| `story_event_rules.trigger_phase` | `AFTER_ACTIVITY` | SQLite v4 호환 분류값. 런타임은 Location만 활동 시작 체크포인트 직후·플레이 화면 직전에 평가 |
| `story_event_rules.selection_policy` | `UNSEEN_FIRST` | 미완료 eligible Story 우선 |
| `story_event_rules.repeat_policy` | `ONCE_PER_RUN` | 같은 회차 재발생 금지 |
| `story_event_rules.requires_location_match` | `1` | 현재 방문 장소 일치 필요 |
| `story_event_rules.limit_group` | `SIDE_STORY` | NPC/Location 공통 제한 그룹 |
| `story_event_conditions` | `PREVIOUS_EVENT_COMPLETE` | 천문대 연속 이야기 선행 조건 |
| `story_choices` | canonical `choiceId` | 선택 의미·표시 기준 |
| `story_choice_effects` | stat / event flag | 서버 권위 선택 결과 |
| `story_event_effects` | StoryProgress COMPLETE | 완료/스킵 공통 결과 |

상세 물리 스키마와 적재 행은 `backend/database/LOCATION_STORY_DB_SPEC.md`를 따른다.

## 11. 회차별 진행 데이터

권위 상태는 Firestore `saveSlots/{slotId}.activeRun`에 둔다.

| 필드 | 의미 |
|---|---|
| `storyProgress[storyId]` | `step / status / lastAdvancedWeek` |
| `eventFlags` | 후속 조건에 필요한 최소 선택/환경 플래그 |
| `pendingStoryEvent` | 선정됐지만 END/SKIP 저장 전인 Story |
| `storyEventWindow.week` | 공통 제한이 속한 주차 |
| `storyEventWindow.sideStoryCount` | 해당 주 NPC+Location 완료/스킵 수 |
| `storyEventWindow.locationStoryCount` | 해당 주 Location 완료/스킵 수, 최대 1 |
| `storyEventWindow.lastResultStoryDay` | 결과 Story 마지막 완료 요일/날짜 |

대사 중간 node 위치, `last_roll_week`, 누적 확률, `effective_unlock_week`는 저장하지 않는다.

## 12. 천문대와 다른 장소를 같은 로직으로 처리

기존 시나리오 문서는 천문대를 연속 이야기, 다른 장소를 생활 이벤트로 구분했지만 실행 시스템에서는 구분하지 않는다. 현재 활성 범위는 천문대 4회와 온실·대서고 각 1회다.

| 시스템 조건 | 천문대 | 온실·대서고 |
|---|---|---|
| 장소 방문 시 후보 판정 | O | O |
| earliest_week | O | O |
| 선행 Story 완료 조건 | O | 불필요 |
| 미완료 Story 우선 | O | O |
| SIDE_STORY 주당 2회·하루 1회 + Location 주 1회 제한 | O | O |
| 고정 확률 증가 | 사용 안 함 | 사용 안 함 |
| 결과 저장 | O | O |

천문대도 DB에서는 `LOC_OBS_01~04` 각각을 canonical Story로 저장하고 `PREVIOUS_EVENT_COMPLETE` 조건으로 순서를 연결한다. 온실·대서고는 독립 1회 Story다.

## 13. 아직 확정이 필요한 시스템 항목

다음은 별도 결정이 필요하다.

- Location Story와 NPC 개별 스토리가 같은 방문에서 동시에 조건을 만족했을 때 우선순위
- 기념품·수집품 보상을 시스템적으로 연결할지
- NPC `WEIGHTED` 선정에 사용할 RNG 구현 방식과 seed 사용 여부

Location 선택의 보이는/보이지 않는 스탯 결과는 `LOCATION_STORY_PRODUCTION.md`의 13개 canonical choice 표로 이미 확정되어 있다. 위 미정 항목은 현재 Location master DB 적재를 막지 않는다.
