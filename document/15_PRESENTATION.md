# LUMIA Final Project 발표자료 원고

> **용도:** Final Project 발표 슬라이드 제작 기준 원고  
> **권장 분량:** 12~13장  
> **발표 흐름:** 문제 정의 → 해결 경험 → AI 핵심 기능 → 기술 설계 → 실제 구현·배포 → 사용자 테스트 → 개선 → 결과

> **공개 원칙:** 공용 저장소에 올리는 발표 자료는 실제 발표본을 그대로 공개하지 않고, 동일한 발표 구조를 보여 주는 **공개용 대체(fake) 자료**를 사용합니다. 실제 발표에서는 운영 화면·실제 시연 캡처 등 필요한 real 자료를 포함한 **비공개 real PPT**를 별도로 사용합니다. 공개용 대체 자료는 발표 산출물의 형식과 흐름을 설명하기 위한 것이며 실제 발표 내용을 대체하지 않습니다.

이 문서는 README를 그대로 복사하지 않고, 심사자가 짧은 발표 안에서 **왜 이 서비스를 만들었는지, 왜 AI가 필요한지, 어떤 기술적 결정을 했는지, 실제 사용자 피드백이 제품에 어떻게 반영됐는지** 이해할 수 있도록 발표 순서를 재구성한 원고입니다.

## Slide 1. LUMIA

### 화면에 넣을 내용

**LUMIA — 52주의 선택을 나만의 미래 이야기로 돌려주는 판타지 생활 육성 게임**

- 대상: 9~11세 어린이
- 플랫폼: Web
- 핵심 AI: 52주 실제 플레이 기록 기반 개인화 엔딩 편지
- Game: `https://lumia-web-six.vercel.app/`

### 발표 핵심 문장

LUMIA는 아이가 52주 동안 수업·모험·관계와 선택을 경험하고, 마지막에 자신이 실제로 만든 기록을 AI가 하나의 미래 이야기로 돌려주는 웹 게임입니다.

## Slide 2. 우리가 해결하고 싶었던 문제

### 화면에 넣을 내용

**“선택을 정답·오답으로 채점하지 않으면서, 아이가 다른 사람의 마음과 여러 관점을 경험하게 할 수 있을까?”**

- 단순한 도덕 점수 대신 인물과 세계의 반응으로 결과 표현
- 서로 다른 성격·배경의 인물과 관계 형성
- 보호자가 아이의 생각을 단정하지 않고 대화를 시작할 수 있는 장기적 가능성

### 발표 핵심 문장

저희는 아이의 선택을 평가하거나 성격을 진단하는 서비스를 만들고 싶지 않았습니다. 선택의 결과를 게임 속 관계와 변화로 경험하고 스스로 생각할 공간을 주는 것이 출발점이었습니다.

## Slide 4. 왜 생성형 AI가 핵심 기능인가

### 화면에 넣을 내용

**고정 엔딩만 사용하면 같은 직업을 얻은 플레이어의 결과가 거의 같습니다.**

LUMIA는:

1. 게임 규칙이 미래 직업을 확정하고
2. 실제 52주 플레이 기록을 선별한 뒤
3. Gemini가 그 기록을 개인화된 회고와 미래 장면으로 표현합니다.

> 사용자 가치: **“게임이 내가 어떻게 플레이했는지 기억하고, 그 기록을 나만의 미래 이야기로 돌려준다.”**

### 발표 핵심 문장

AI는 랜덤 문장을 붙이기 위한 기능이 아니라 긴 플레이의 결과를 개인적인 서사 보상으로 바꾸기 때문에 핵심 기능으로 사용했습니다.

## Slide 5. 과제 필수 AI 기술 2종

### 화면에 넣을 내용

### Long-term Memory

- 여러 주차와 로그인 세션의 활동·중요 선택을 Firestore에 누적
- 52주 종료 시 다시 읽어 AI 입력으로 실제 사용
- 회차별로 격리하여 이전 회차 기억과 자동 혼합하지 않음

### Automated Workflow

```text
직업 판정
→ 장기 기록 로드
→ 대표 기록 선별
→ Gemini 호출
→ 결과 검증
→ 재시도 / fallback
→ 저장
→ 엔딩 표시
→ 회차 완료
```

### 발표 핵심 문장

Long-term Memory는 무엇을 기억할지에 대한 기술이고, Automated Workflow는 그 기억을 실제 AI 결과로 바꾸는 실행 파이프라인입니다.

## Slide 6. AI와 게임 규칙의 책임을 분리한 이유

### 화면에 넣을 내용

| 게임 규칙이 결정 | Gemini가 표현 |
|---|---|
| 최종 직업 | 실제 기록의 자연어 회고 |
| 보상·해금 | 미래 장면과 응원 |
| 회차 완료 | 문체와 서사적 표현 |

안전 장치:

- 실제 저장 기록과 작가 작성 선택 요약만 AI Context에 전달
- 성격·심리·진로 진단 금지
- 존재하지 않은 플레이 사실 생성 금지
- 금지 표현·길이·직업명·캐릭터명·원시 스탯 노출 검증
- Gemini 실패 시 검수된 fallback 편지
- 생성 완료 편지는 저장하여 재접속 시 중복 호출 방지

### 발표 핵심 문장

AI에게 게임 결과를 결정할 권한을 주지 않고 표현만 맡겨 재현성과 어린이 대상 안전성을 확보했습니다.

## Slide 7. 시스템 아키텍처

### 화면에 넣을 내용

```text
[Player]
   ↓
Vercel — Phaser 3 + JavaScript/Vite
   ↓ Firebase Auth
Render — FastAPI
   ├─ Firestore
   ├─ SQLite Content Master
   └─ Gemini API

[Operator]
   ↓
Vercel — Next.js + Tailwind CSS Admin
   ↓ Firebase Auth + admin 권한
FastAPI /admin/*
```

- 게임 상태·보상·엔딩은 서버가 검증
- Gemini API Key / Firebase Admin Credential은 서버에만 저장
- 게임과 관리자 UI는 별도 배포

## Slide 8. 기술 선택과 의사결정

### 화면에 넣을 내용

| 영역 | 선택 | 이유 |
|---|---|---|
| Game | Phaser 3 | 브라우저 우선 2D, WebGL/Canvas, JS 생태계 직접 연결 |
| Admin | Next.js + Tailwind CSS | 표·검색·통계·Form 중심 DOM 업무 UI |
| Backend | FastAPI | 게임 규칙·Firebase Admin·Gemini를 서버에 분리 |
| Auth / DB | Firebase Auth + Firestore | 계정 인증과 사용자별 문서형 상태 |
| Deploy | Vercel + Render | 프론트와 API 운영 책임 분리 |

### 발표 핵심 문장

Phaser는 기존 데모를 사용했기 때문이 아니라 웹 2D 게임이라는 제품 특성에 맞춰 선택했고, 관리자 화면은 게임 Canvas와 성격이 달라 Next.js로 분리했습니다.

## 발표 준비 체크

- 게임 URL과 관리자 URL이 발표 당일 접속되는지 확인
- Render cold start 가능성을 고려해 발표 전에 `/health` 호출
- 시연용 계정의 이메일 인증과 Save Slot 상태 확인
- 52주 엔딩 시연용 슬롯을 미리 준비하고 Gemini 생성 결과가 저장돼 있는지 확인
- 인터넷 장애에 대비해 게임 화면·엔딩 편지·관리자 화면 캡처를 준비
- **공용 저장소에는 공개용 대체(fake) 발표 자료만 등록하고 실제 발표용 real PPT는 별도 비공개 공간에서 관리**
- 실제 발표용 real PPT에도 Firebase 서비스 계정, Gemini API Key, ID Token, 실제 사용자 이메일을 노출하지 않음
- 사용자 테스트 참가자는 T01~T05 익명 정보만 사용
