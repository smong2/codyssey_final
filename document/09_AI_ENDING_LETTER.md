# AI 핵심 기능 — 개인화 엔딩 편지

## 1. 기능 정의

LUMIA의 생성형 AI 핵심 기능은 **52주 플레이가 끝난 뒤, 게임 시스템이 확정한 미래 직업 엔딩과 실제 플레이 기록을 바탕으로 플레이어 개인에게 맞는 엔딩 편지를 생성하는 것**입니다.

AI는 직업 엔딩 자체를 임의로 결정하지 않습니다. 직업 엔딩 판정은 재현 가능한 게임 규칙으로 처리하고, AI는 그 결과와 플레이 기록을 자연어로 해석해 개인화된 편지로 전달합니다.

핵심 원칙은 다음과 같습니다.

> **게임 시스템이 “어떤 미래인가”를 결정하고, AI는 “그 미래가 이번 플레이어의 52주와 어떻게 이어지는가”를 편지로 표현한다.**

엔딩 화면의 질문 **`무엇을 지켰니?`** 는 작가가 작성한 고정 문구이며 AI 출력이 아닙니다. AI는 `네가 지킨 것은 ○○야`처럼 이 질문의 정답을 대신 판정하지 않고, 실제 52주 기록을 회고해 플레이어가 스스로 답을 느낄 수 있게 합니다.

## 2. 전체 처리 흐름

```text
52주 플레이 완료
→ 엔딩 조건 판정
→ 정규 직업 엔딩 10종 중 후보 판정
→ 후보가 없으면 fallback 직업 `별길 개척자` 확정
→ 이번 회차의 대표 플레이 기록 추출
→ AI 편지 입력 데이터 구성
→ 생성형 AI가 개인화 엔딩 편지 생성
→ 형식·금지 표현·필수 항목 검증
→ 엔딩 화면에서 고정 문구 `무엇을 지켰니?` 노출
→ 확정 직업과 개인화 편지 노출
→ 엔딩 결과 및 필요한 메타 기록 저장
```

엔딩 후보 산출과 복수 후보 우선순위는 [엔딩 시스템](content/02_STATS_EVENTS_ENDINGS/03_ENDINGS.md)의 규칙을 따릅니다.

## 3. AI가 받는 입력

AI에는 원시 게임 데이터 전체를 그대로 전달하지 않고, 편지 생성에 필요한 **정리된 엔딩 컨텍스트**만 제공합니다.

| 입력 | 내용 |
|---|---|
| 캐릭터 | 현재 회차의 플레이 캐릭터 이름·ID |
| 확정 직업 엔딩 | ID·직업명·작가 부제·`CAREER/FALLBACK` 유형·고정 `careerAnchor`·`futureSceneGuide`·대표/보조 스탯 |
| 보이는 스탯 | 5개 최종 성장 스탯. AI는 내부 판단에 사용하되 편지에 원시 숫자를 나열하지 않음 |
| 보이지 않는 스탯 요약 | 값이 0보다 큰 항목 중 상위 최대 3개. 동률은 고정 스탯 순서 사용 |
| 대표 플레이 기록 | 백엔드 규칙으로 선별한 실제 횟수형 기록 4~6개 |
| 중요 선택 | `importantChoice=true`인 실제 선택 중 최대 2개. 대표 사건 목록은 보내지 않음 |
| 표현 규칙 | 대상 연령, 문체, 금지 표현, 길이, 필수 섹션 |

정규 직업의 `name / subtitle / careerAnchor / futureSceneGuide`는 작가 문서 `story/ending/ENDING_STORY.md`에서 채택한 고정 원고를 엔딩 마스터에 구조화한 값입니다. AI는 이 의미를 다른 직업이나 다른 미래로 바꾸지 않습니다.

`ending.type = FALLBACK`이면 `subtitle`, `primaryStat`, `secondaryStat`, `futureSceneGuide`는 별도 fallback 값 또는 `null`일 수 있습니다. 대표 사건·발견 목록 전체를 AI에 전달하지 않습니다.

### 플레이 기록 4~6개 선별

정규 직업은 [엔딩 시스템](content/02_STATS_EVENTS_ENDINGS/03_ENDINGS.md)에 정의한 직업별 우선 기록을 먼저 넣고, 아래 공통 기록을 순서대로 채웁니다.

`전체 수업 → 모험 → NPC 만남 → 미니게임 클리어 → NPC 스토리 완료 → 장소 발견 → 특별 아이템·발견물 → 중요 선택`

- 직업별 우선 기록은 최대 2개를 먼저 선택합니다.
- 중복 type은 한 번만 넣습니다.
- 값이 0인 항목은 우선 제외합니다.
- 비중복·0 초과 기록만으로 4개가 되지 않을 때만 0인 공통 기록을 사용해 최소 4개를 맞춥니다.
- 최대 6개에서 중단합니다.
- `별길 개척자`는 직업별 우선 기록 없이 공통 기록 순서를 사용합니다.

선별된 기록의 **라벨과 숫자는 UI가 직접 `아르카디아에서의 기록`으로 렌더링**합니다. AI는 이 값을 해석할 수 있지만 숫자 목록을 다시 생성하지 않습니다.

### 중요 선택 최대 2개 선별

- 콘텐츠 마스터에서 `importantChoice = true`인 선택만 후보입니다.
- 별도의 엔딩 전용 태그를 새로 만들지 않고 **더 최근 주차의 중요 선택을 우선**합니다.
- 최대 2개만 전달하며 후보가 없으면 빈 배열을 사용합니다.
- AI에 보내는 `summary`는 작가/기획이 마스터 데이터에 작성한 짧은 사실 문장입니다. AI가 선택 내용을 추측해 만들지 않습니다.

## 4. AI가 생성하는 편지

엔딩 편지는 최소 다음 세 부분을 포함합니다.

1. **이번 이야기에서의 미래 직업** — 규칙 엔진이 확정한 직업을 알려 줍니다. AI가 다른 직업으로 변경하지 않습니다.
2. **52주 플레이 기록 회고** — 실제 횟수 기록과 전달받은 중요 선택만 사용합니다. 대표 사건을 별도로 추측하거나 존재하지 않은 일을 만들어 내지 않습니다.
3. **미래 모습과 응원** — 이번 회차의 성장 방향과 플레이 방식을 바탕으로, 해당 직업에서 어떤 방식으로 행동할지 긍정적인 가능성을 상상하고 응원 메시지로 마무리합니다.

같은 직업 엔딩이라도 플레이 경향이 다르면 편지의 미래 모습도 달라질 수 있습니다.

AI 편지는 `무엇을 지켰니?`에 대한 단일 정답을 생성하지 않습니다. 대신 실제 플레이 기록과 필요한 경우 중요 선택을 자연스럽게 되짚어 주고 그 경험이 이번 직업 엔딩과 어떻게 이어지는지를 설명합니다.

| 플레이 경향 | 편지에서 그릴 수 있는 미래 모습 |
|---|---|
| 솜씨·용기·독립성이 두드러짐 | 상황을 빠르게 파악하고 먼저 행동하는 모습 |
| 책임·협력·신중함이 두드러짐 | 동료와 역할을 나누고 모두의 안전을 확인하는 모습 |
| 공감·표현력·책임이 두드러짐 | 상대를 안심시키고 주변 사람과 침착하게 소통하는 모습 |

이 차이는 직업의 우열이나 성격 평가가 아니라 **이번 플레이에서 보여 준 서로 다른 방식**을 반영합니다.

## 5. 게임 규칙과 AI의 책임 경계

| 처리 | 담당 |
|---|---|
| 엔딩 후보 조건 계산 | 게임 규칙 / 백엔드 |
| 미노출 우선·적합도·동률 판정 | 게임 규칙 / 백엔드 |
| 최종 직업 엔딩 확정 | 게임 규칙 / 백엔드 |
| 대표 플레이 기록 선별 | 백엔드 규칙을 우선하며 AI 입력용으로 가공 |
| `아르카디아에서의 기록` 라벨·횟수 표시 | 게임 UI / 백엔드 선별 데이터 |
| `무엇을 지켰니?` 고정 문구 표시 | 게임 UI / 고정 원고 |
| 플레이 기록의 자연어 해석 | 생성형 AI |
| 미래 직업에서의 모습 상상 | 생성형 AI |
| 응원 메시지 작성 | 생성형 AI |
| 편지의 필수 항목·금지 표현 검증 | 백엔드 |

이 구조를 사용하면 같은 플레이 데이터에 대한 직업 판정은 재현 가능하게 유지하면서, 편지 표현은 개인화할 수 있습니다.

## 6. 어린이 대상 표현 원칙

주 대상이 9~11세이므로 AI 편지는 게임 기록을 어린이의 실제 성격·심리·진로에 대한 진단처럼 표현하지 않습니다.

- `너는 원래 이런 사람이야`처럼 실제 성격을 단정하지 않습니다.
- `책임감이 부족하다`, `용기가 낮다` 같은 부정적 성격 평가를 하지 않습니다.
- 내부 스탯 점수와 순위를 직접 보여 주며 평가하지 않습니다.
- 미래 직업을 실제 진로 예측이나 운명처럼 단정하지 않습니다.
- `무엇을 지켰니?`에 대해 하나의 정답을 단정하거나 플레이어의 가치관을 대신 규정하지 않습니다.
- 플레이하지 않은 사건·행동·관계를 사실처럼 만들어 내지 않습니다.
- 플레이어를 다른 사람과 비교하지 않습니다.
- 불필요한 개인정보를 AI 입력에 포함하지 않습니다.

권장 표현은 `아르카디아에서 보여 준 모습을 보면...`, `이번 이야기에서 너는 ...하는 모습을 자주 보여 줬어.`, `이번 이야기에서 그려진 미래는 ...이야.`처럼 **게임 안의 경험**임을 명확하게 합니다.

## 7. 실패·오류 대응

AI 호출 실패 때문에 52주 엔딩 자체가 막히면 안 됩니다.

1. 직업 엔딩은 AI 호출 전에 확정·저장할 수 있어야 합니다.
2. AI 응답이 실패하거나 검증을 통과하지 못하면 재시도 정책을 적용합니다.
3. 재시도 후에도 생성할 수 없으면 직업별 안전한 기본 편지 템플릿을 사용합니다.
4. AI 실패가 엔딩·해금·다음 회차 데이터의 정합성에 영향을 주지 않게 합니다.

세부 재시도 횟수와 timeout은 API 구현 단계에서 결정합니다.

플레이어 화면에는 Gemini·모델·검증 오류 같은 기술 정보를 직접 노출하지 않습니다. AI 재시도 후 고정 fallback 편지가 준비되면 정상 편지와 동일한 엔딩 화면으로 표시합니다. 서버/네트워크 문제로 엔딩 결과 자체를 읽지 못할 때만 일반적인 `편지를 불러오지 못했습니다 / 다시 시도` 상태를 제공합니다.

### `별길 개척자` 편지 원칙

정규 직업의 필수 조건을 하나도 만족하지 못했을 때 게임 규칙이 `ENDING_STARPATH_PIONEER`를 확정합니다. AI는 이를 실패로 해석하지 않습니다.

권장 핵심 메시지:

> 아르카디아에서 보낸 52주는 한 가지 이름으로 다 담기 어려웠어. 너의 미래는 `별길 개척자`야. 아직 하나의 길에 자신을 묶기보다 여러 길을 직접 걸어 보며 새로운 가능성을 찾는 사람이란다.

AI 생성 시에는 실제 플레이 기록과 성장 방향을 덧붙여 개인화하되 `조건 미달`, `실패`, `부족함`, `꽝` 같은 표현을 금지합니다.

### 고정 영역 / AI 생성 영역 / fallback 영역

| 영역 | 생성 주체 | 규칙 |
|---|---|---|
| `무엇을 지켰니?` | 고정 원고/UI | AI 입력·출력과 분리 |
| 직업명 | 엔딩 마스터 | AI 변경 금지 |
| 작가 부제 | 엔딩 마스터 / 작가 원문 | AI 변경 금지 |
| `careerAnchor` | 엔딩 마스터 / 작가 원문의 직업 의미 | AI가 의미를 뒤집지 않음 |
| `futureSceneGuide` | 엔딩 마스터 / 작가 원문의 미래 장면 방향 | AI 미래 묘사의 범위를 제한 |
| `아르카디아에서의 기록` 4~6개 | 백엔드 선별 + UI | 라벨·숫자를 AI가 재작성하지 않음 |
| 성장 회고 | AI | 전달받은 스탯·기록만 사용 |
| 중요 선택 회고 | AI | 전달된 선택이 있을 때만 사용 |
| 미래 모습·응원 | AI | 게임 세계의 가능성으로 표현 |
| AI 최종 실패 시 본문 | 고정 fallback 템플릿 | 직업명·careerAnchor·실제 기록은 그대로 유지 |

AI 최종 실패 시에도 `무엇을 지켰니? → 직업명·작가 부제 → careerAnchor → 아르카디아에서의 기록`은 모두 정상 노출할 수 있습니다. 본문만 안전한 고정 문장으로 대체하므로 엔딩 결과와 저장·해금 처리는 영향을 받지 않습니다.

고정 fallback 본문은 다음 골격을 사용합니다.

```text
[캐릭터 이름]에게

아르카디아에서 보낸 52주 동안 너는 여러 경험을 하며 너만의 길을 만들어 왔구나.
이번 이야기에서 이어진 미래는 「[직업명]」이야.
[careerAnchor]

한 해 동안 남긴 기록을 돌아보면 네가 직접 해 본 일들이 다음 길의 좋은 출발점이 되어 줄 거야.
```

## 8. Final Project의 AI 핵심 기능으로서의 의미

생성형 AI는 단순 장식 문구를 무작위로 만드는 데 사용하지 않습니다. 플레이어가 52주 동안 축적한 서로 다른 행동·선택·성장 기록을 **개인화된 서사적 보상**으로 변환하는 마지막 단계에 사용합니다.

비AI 방식이라면 직업별 고정 편지 몇 종류를 미리 작성해야 하므로, 같은 직업을 얻은 플레이어들은 거의 같은 결과를 보게 됩니다. AI를 사용하면 동일한 직업 엔딩 안에서도 실제 플레이 기록과 성장 방향에 따라 서로 다른 회고와 미래 모습을 제공할 수 있습니다.

핵심 사용자 가치는 다음과 같습니다.

> **“내가 52주 동안 어떻게 플레이했는지 기억하고, 그 기록을 나만의 미래 이야기로 돌려받는 경험.”**

## 9. Final Project 요구사항과 AI 기술 선택

### 9.1 무엇이 필수인가

Final Project 요구사항은 다음 두 조건을 별도로 요구합니다.

1. **생성형 AI 또는 AI Agent가 서비스의 핵심 기능이어야 합니다.**
2. `AI Agent / RAG / 멀티모달 AI / 자동화 워크플로우 / Long-term Memory` 다섯 기술 요소 중 **두 가지 이상**을 실제 서비스에 포함해야 합니다.

따라서 `AI 기능을 두 개 만들어야 한다`는 의미가 아닙니다. LUMIA는 **Gemini 개인화 엔딩 편지**를 핵심 생성형 AI 기능으로 사용하고, 기술 요소는 **자동화 워크플로우 + Long-term Memory** 두 가지를 선택합니다.

별도의 AI Agent는 제출 버전에 넣지 않습니다. 현재 엔딩 처리는 순서와 책임이 명확하므로 AI가 다음 행동이나 도구를 자율적으로 선택하게 만드는 것보다, 검증 가능한 워크플로우로 구현하는 편이 게임 규칙의 재현성과 어린이 대상 안전성에 더 적합합니다.

### 9.2 AI Agent를 사용하지 않는 이유

AI Agent는 보통 `목표를 받음 → 상황 판단 → 필요한 도구 선택 → 결과 확인 → 다음 행동 결정`처럼 AI가 다음 행동을 일부 자율적으로 결정해야 할 때 유용합니다.

LUMIA의 엔딩은 다음처럼 처리 순서를 미리 정할 수 있습니다.

```text
52주 종료
→ 게임 규칙으로 직업 확정
→ 장기 플레이 기억 조회
→ AI 입력 구성
→ 편지 생성
→ 검증
→ 저장·표시
```

AI가 직업을 바꾸거나 임의의 게임 데이터를 골라 판단할 이유가 없습니다. 오히려 이런 권한을 Agent에게 넘기면 같은 플레이 기록에서도 결과가 달라질 가능성이 커지고, 존재하지 않은 기록을 선택하거나 어린이의 성격·진로를 과도하게 판단할 위험이 생깁니다.

따라서 제출 버전에서는 **생성형 AI + 명시적인 서버 워크플로우**를 사용합니다.

향후 Agent를 적용한다면 `부모/보호자 피드백 고도화`가 더 자연스러운 후보입니다. 예를 들어 보호자가 `지난 회차와 이번 회차에서 달라진 점이 뭐야?`라고 질문했을 때 Agent가 현재 회차 통계, 과거 Ending Record, 활동 기록 중 필요한 조회 도구를 선택하고 이해하기 쉬운 피드백을 구성할 수 있습니다. 이 기능은 Final Project 제출 범위에는 포함하지 않습니다.

### 9.3 자동화 워크플로우란 무엇인가

자동화 워크플로우는 **여러 시스템 작업을 사람이 매번 실행하지 않아도 정해진 순서와 조건으로 이어서 처리하는 파이프라인**입니다.

LUMIA에서는 다음 전체 흐름이 하나의 AI 자동화 워크플로우입니다.

```text
52주 종료
→ 규칙 엔진이 직업 엔딩 확정
→ 사용자별 Long-term Play Memory 로드
→ 대표 플레이 기록 4~6개 선별
→ 중요 선택 최대 2개 선별
→ Gemini 입력 컨텍스트 구성
→ Gemini API 호출
→ 응답 형식·금지 표현·필수 내용 검증

정상
→ 최종 편지 확정

실패
→ 허용된 재시도
→ 계속 실패하면 안전한 fallback 편지 확정

→ 직업·편지 준비 결과 안전 저장
→ 엔딩 화면 표시
→ 최종 `타이틀로`
→ 본 엔딩 기록·회차 완료·Global Meta를 한 번만 확정
```

Gemini API를 한 번 호출하는 것만을 `워크플로우`라고 부르지 않습니다. **게임 규칙, 장기 기억 조회, AI 호출, 검증, 오류 처리, 저장과 화면 표시가 자동으로 연결된 전체 처리**가 기술 요소입니다.

엔딩 화면 표시 도중 종료되면 준비 저장한 같은 편지를 다시 사용하며 AI를 재호출하지 않습니다. `seenEndingIds`, `endingViewCounts`와 엔딩 열람에 의존하는 메타·해금은 최종 `타이틀로` 저장 성공 시점에 반영합니다.

### 9.4 Long-term Memory는 일반 게임 세이브와 다릅니다

Firestore에 게임 데이터를 오래 저장하는 것만으로 Long-term Memory라고 주장하지 않습니다. 일반 세이브는 원래 게임을 이어 하기 위해 필요한 기능이기 때문입니다.

LUMIA에서 사용하는 Long-term Memory는 정확히는 **`Long-term Play Memory`**, 즉 **AI가 나중에 개인화를 위해 다시 사용하는 사용자별 장기 플레이 기억**입니다.

| 구분 | 일반 게임 세이브 | Long-term Play Memory |
|---|---|---|
| 목적 | 게임 진행 상태 복원 | AI가 과거 플레이 맥락을 기억하고 개인화에 사용 |
| 저장 대상 | 현재 주차, 체력, 일정, phase 등 | 누적 활동, 중요 선택, 성장 방향, 엔딩 관련 기억 |
| 다시 읽는 시점 | 이어 하기 | 52주 종료 후 엔딩 AI 생성 직전 |
| AI 결과에 영향 | 없어도 됨 | Gemini 입력에 반드시 반영 |

따라서 완료 조건은 `DB에 오래 저장했다`가 아니라 **`여러 세션에 걸쳐 저장한 사용자 기억을 나중에 다시 불러와 실제 AI 생성 입력으로 사용했다`**입니다.

### 9.5 기억은 언제 쌓이는가

Long-term Play Memory는 엔딩 직전에 한 번 만드는 데이터가 아닙니다. 플레이 도중 발생한 의미 있는 결과를 **안정 저장 경계에서 계속 누적**합니다.

#### 활동 완료 시

수업·모험·미니게임·NPC/Location 활동이 정상 종료되면 해당 회차의 누적 플레이 기록을 갱신합니다.

예:

```text
3주차 화요일 모험 완료
→ adventureCount + 1
→ locationDiscoveryCount 갱신
→ 성장 결과 반영
→ 안정 저장 경계에서 계정 데이터에 보존
```

#### 중요 선택 확정 시

Main/NPC/Location Story에서 `importantChoice = true`인 선택이 확정되면 다음과 같은 사실 기반 기록을 보존합니다.

```text
49주차 MS05
→ SHARE_FACTS_FIRST 선택 확정
→ eventId / choiceId / week 저장
```

선택의 `summary` 원문은 사용자 세이브에 중복 저장하지 않고 콘텐츠 마스터의 `eventId + choiceId`로 조회합니다. 52주 종료 시 AI Memory Context를 만들 때 작가/기획이 작성한 짧은 사실 문장을 결합하며, AI가 선택 내용을 추측해 만들지 않습니다.

#### 주간 저장과 세션 종료

금요일·주말 처리가 끝나 주간 저장이 확정되면 그 주까지 누적한 기록을 계정에 보존합니다. 브라우저를 닫거나 로그아웃해도 사라지지 않습니다.

```text
1~8주 플레이
→ 로그아웃

다음 접속
→ 같은 계정의 기존 플레이 기록 로드
→ 9주차부터 계속 플레이
→ 기존 기록 위에 새 기록 누적

...

52주 완료
```

이처럼 **한 번의 브라우저 세션을 넘어 유지되는 사용자별 플레이 기억**이 Long-term Memory의 핵심입니다.

### 9.6 기억은 언제 사용하는가

Final Project 제출 버전에서는 Long-term Play Memory를 **현재 회차 52주 엔딩 편지를 생성하는 시점에 집중적으로 사용**합니다.

```text
52주차 플레이 완료
→ 12월 31일 마지막 주간 요약
→ 게임 규칙으로 직업 엔딩 확정
→ 현재 회차 Long-term Play Memory 로드   ← 장기 기억 사용 시점
→ AI에 필요한 기록 4~6개 선별
→ 중요 선택 최대 2개 선별
→ 성장 방향 요약
→ AI Memory Context 생성
→ 확정 직업 정보와 결합
→ Gemini 입력에 실제 포함
→ 개인화 엔딩 편지 생성
```

즉 **52주 동안 기억을 쌓고, 마지막에 그 기억을 꺼내 플레이어에게 개인화된 엔딩으로 돌려줍니다.** 플레이 중 매일 Gemini를 호출하는 구조가 아닙니다.

### 9.7 AI Memory Context

Firestore의 Save Slot 전체를 Gemini에 그대로 보내지 않습니다. UI phase, 네트워크 복구 상태, 임시 일정 내부값 등 AI가 알 필요 없는 데이터는 제외합니다.

백엔드가 장기 플레이 기록에서 편지에 의미 있는 내용만 선별해 **AI Memory Context**를 구성합니다.

```json
{
  "playRecords": [
    {"type": "adventureCount", "label": "모험을 떠난 횟수", "count": 46},
    {"type": "locationDiscoveryCount", "label": "새로운 장소를 발견한 횟수", "count": 13}
  ],
  "representativeChoices": [
    {
      "eventId": "MS05",
      "choiceId": "SHARE_FACTS_FIRST",
      "week": 49,
      "summary": "확인된 사실과 아직 모르는 점을 모두에게 먼저 알리기로 했다"
    }
  ],
  "growthHighlights": ["exploration", "curiosity", "independence"]
}
```

이 Context는 별도 벡터 DB나 대화형 메모리 프레임워크를 요구하지 않습니다. 구조화된 게임 데이터가 이미 있으므로 Firestore를 단일 원본으로 두고, 백엔드가 AI에 필요한 장기 기억을 조회·선별하는 방식이 더 단순하고 검증하기 쉽습니다.

구현에서는 일반 세이브 로드와 AI 메모리 구성을 책임 수준에서 구분합니다. 예를 들면 `load_long_term_play_memory()` 또는 동등한 서비스에서 현재 회차의 장기 기록을 읽고, `build_ending_memory_context()`에서 Gemini 입력에 필요한 기억만 선별하는 식입니다. 실제 함수명은 개발 단계에서 달라질 수 있습니다.

### 9.8 회차가 끝난 뒤 기억은 어떻게 보관하는가

현재 회차의 편지 생성이 완료되면 **최종 편지와 편지에 사용한 대표 기억을 Ending Record에 보존**합니다.

```text
1회차 Long-term Play Memory
→ 1회차 엔딩 편지 생성에 사용
→ 직업 엔딩 + 최종 편지 + 사용한 대표 기록을 Ending Record에 보존

2회차 시작
→ 2회차의 Long-term Play Memory를 새로 누적
→ 2회차 편지는 2회차 기록만 사용
```

Final Project 제출 버전에서는 **이전 회차의 플레이 기억을 다음 회차의 AI 편지에 섞지 않습니다.** 과거 Ending Record는 사용자가 이전 엔딩 결과를 다시 보는 용도로 보존합니다.

제출 후 부모/보호자 피드백을 고도화할 경우 여러 회차의 Ending Record를 비교하는 장기 기억으로 확장할 수 있습니다.

### 9.9 Long-term Memory 전체 생명주기

```text
[기억 축적]
주간 활동·중요 선택 발생
→ 누적 플레이 기록 갱신
→ 안정 저장 경계에서 Firestore 보존
→ 로그아웃/재접속 후에도 유지
→ 다음 주차 기록 계속 누적

[기억 사용]
52주 종료
→ 현재 회차 장기 플레이 기억 로드
→ 대표 기록 4~6개 + 중요 선택 최대 2개 선별
→ AI Memory Context 생성

[AI Workflow]
직업 엔딩 정보 + AI Memory Context
→ Gemini 호출
→ 검증 / 재시도 / fallback
→ 최종 편지 확정
→ 엔딩 화면 표시

[보관]
직업 엔딩 + 최종 편지 + 사용한 대표 기억
→ 회차별 Ending Record 저장
```

### 9.10 두 기술 요소의 차이와 연결

- **Long-term Memory**: AI가 사용할 과거 사용자 맥락을 여러 세션에 걸쳐 기억하는 기술
- **자동화 워크플로우**: 그 기억을 실제 AI 결과로 바꾸기 위해 여러 시스템 단계를 자동으로 연결하는 기술

관계는 다음과 같습니다.

```text
Long-term Play Memory
        ↓
자동화 AI Workflow에서 조회·사용
        ↓
Gemini 개인화 엔딩 편지
```

두 항목은 같은 기능을 이름만 다르게 부른 것이 아닙니다. 하나는 **기억할 데이터와 사용 시점**, 다른 하나는 **그 기억을 처리하는 실행 파이프라인**을 담당합니다.

### 9.11 제출 시 구현 증거

Long-term Memory는 문서 설명만으로 완료 처리하지 않습니다. WBS 10.1.4에서 다음 증거를 확보합니다.

1. 초반 주차의 플레이 기록과 중요 선택이 계정 데이터에 저장됨
2. 로그아웃·재접속 후에도 동일 기록이 유지됨
3. 후반 주차까지 기록이 계속 누적됨
4. 52주 종료 시 백엔드가 과거 여러 주차의 기록을 다시 읽음
5. 대표 기록 4~6개와 중요 선택 최대 2개가 AI Memory Context에 들어감
6. 해당 Context가 실제 Gemini 요청에 포함됨
7. 서로 다른 플레이 기록을 가진 사용자/테스트 케이스가 서로 다른 Context와 편지를 생성함
8. 최종 편지와 사용한 대표 기억이 Ending Record에 저장되고 재조회 시 AI를 다시 호출하지 않음

가장 이해하기 쉬운 시연은 `모험 중심 플레이`와 `수업/NPC 중심 플레이` 두 테스트 데이터를 만들어 서로 다른 Memory Context와 개인화 편지가 생성되는 것을 비교하는 방식입니다.

### 9.12 선택하지 않은 기술 요소

- **AI Agent**: 현재 엔딩에는 자율적인 도구 선택이 필요하지 않아 제출 버전에서 제외합니다. 제출 후 부모/보호자 피드백 고도화의 후보로 둡니다.
- **RAG**: 엔딩에 필요한 직업·스토리 정보가 구조화된 게임 마스터 데이터로 이미 정해져 있어 별도 검색·벡터 DB를 추가하지 않습니다.
- **멀티모달 AI**: 현재 AI 입력과 출력이 텍스트·구조화 게임 기록 중심이므로 제출 조건을 맞추기 위해 이미지·음성 AI를 억지로 추가하지 않습니다.

## 10. 구현 사양과 기획의 경계

AI 기능의 **제품 기획 계약**은 다음까지 확정합니다.

- AI가 왜 필요한지와 사용자 가치
- AI가 받는 데이터 범위
- AI가 생성해야 하는 내용
- 직업 판정과 AI의 책임 경계
- 어린이 대상 금지 표현·개인정보 경계
- 실패 시 엔딩을 막지 않고 fallback을 사용하는 정책
- Long-term Play Memory의 축적·사용·보관 시점
- 자동화 워크플로우의 단계와 오류 경계

아래 항목은 별도의 게임 기획 결정이 아니라 **백엔드 구현·테스트 단계에서 시스템 환경에 맞춰 결정하는 개발 파라미터**로 관리합니다.

- 실제 system/task prompt 문구와 구조화 출력 schema
- 모델명과 thinking/temperature 등 모델 설정
- 목표 글자 수와 최대 출력 token
- timeout
- 재시도 횟수와 backoff
- JSON/필수 필드 validation 구현 방식
- 금지 표현 필터 구현 방식
- API 호출 횟수·비용 제한

이 값들은 어린이 대상 안전 규칙과 본 문서의 데이터 계약을 바꾸지 않는 범위에서 백엔드 담당자가 합리적인 기본값을 적용하고 실제 Gemini 테스트 결과에 따라 조정합니다. 환경별 값은 가능한 한 환경변수/설정으로 분리합니다.

- 생성형 AI 제공자는 **Gemini API**로 확정합니다.
- 기본 모델은 **`gemini-3.8-flash`**로 두고 `GEMINI_MODEL` 환경변수로 변경할 수 있게 합니다.
- 초기 `GEMINI_THINKING_LEVEL`은 `low`로 두되 실제 편지 품질·응답시간 테스트에 따라 조정할 수 있습니다.
- 생성된 최종 편지는 **회차별 Ending Record에 영구 저장**하며 같은 엔딩을 다시 보아도 과거 편지를 덮어쓰지 않습니다. 재조회할 때 새로 생성하지 않습니다.

Final Project의 최종 기술 요소 2종은 **자동화 워크플로우 + Long-term Memory**로 유지합니다. 단, Long-term Memory는 일반 세이브 저장만으로 완료 처리하지 않고 위 `Long-term Play Memory` 조회·AI 입력 사용과 테스트 증거까지 확인합니다. 실제 검증은 WBS 10.1.4에서 수행합니다.

## 11. 관련 문서

현재 엔진 UI 시안에는 확정 직업/3개 편지 섹션의 표시 프레임과 결과 조회 adapter 연결 지점이 있습니다. 사용자가 승인한 짧은 예시 편지로 화면을 확인할 수 있지만 실제 AI 출력·정식 직업 판정이나 회차 완료가 아닙니다. 현재 회차 실제 활동 기록은 예시와 별도로 표시합니다. 백엔드 endpoint·생성·안전 검증·fallback·엔딩 저장은 후속이며 위 본편 기획을 변경하지 않습니다. 확인 경로와 엔진 내부 표시 모델 제안은 [엔진 프레임 안내](../engine/ENDING_FRAME.md)를 참고합니다.

정상 엔딩의 화면 순서는 `무엇을 지켰니? → 미래 직업 공개 → 개인화 편지 + 아르카디아에서의 기록 → 신규 해금이 있을 때만 해금 요약 → 타이틀`이며 상세 화면 계약은 [기능 프레임](content/11_FEATURE_FRAME.md)을 따릅니다. 개발 미리보기용 `X → 마이룸`은 실제 52주 엔딩 동작으로 사용하지 않습니다.
