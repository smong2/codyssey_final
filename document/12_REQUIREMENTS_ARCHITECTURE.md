# 기능·비기능 요구 명세와 시스템 아키텍처

이 문서는 WBS 10.1.2의 기준 문서입니다. Final Project 제출에서 요구하는 기능 요구사항, 비기능 요구사항, 시스템 구조, 기술 선택 경계를 LUMIA 기준으로 정리합니다.

## 1. 시스템 범위

LUMIA의 제출 범위는 다음 네 영역으로 구분합니다.

1. **게임 클라이언트** — 52주 플레이, 수업·모험·휴식, 이벤트, 수집·해금, 엔딩 UI
2. **계정·저장 API** — Firebase 인증, 5개 세이브 슬롯, Global Meta, 플레이 기록
3. **AI 엔딩** — 규칙 기반 직업 판정 후 Gemini 개인화 편지 생성
4. **기록 조회 페이지** — 동일 사용자 계정으로 로그인하여 플레이 기록과 엔딩 편지를 읽기 전용으로 확인하는 최소 관리/보호자용 화면

별도의 운영자용 CMS, 사용자 검색·정지, 콘텐츠 편집, 통계 대시보드 같은 관리자 기능은 Final Project 시간 범위에서 제외합니다.

## 3. 최소 기록 조회 페이지

기존에는 보호자가 아이의 플레이를 확인하는 별도 기능을 검토했지만, Final Project 범위에서는 **간단한 읽기 전용 기록 확인 화면**으로 축소합니다.

### 인증

- 게임 계정과 동일한 Firebase Email/Password 인증을 사용합니다.
- 페이지가 별도로 사용자 비밀번호를 저장하거나 관리자용 공용 비밀번호를 두지 않습니다.
- 로그인 성공 후 Firebase ID Token으로 FastAPI에 조회 요청을 보내고 서버가 UID를 확인합니다.
- 조회 대상 UID는 인증된 본인 UID로 고정합니다.

### 표시 정보

- 계정의 회차 완료 횟수
- 마지막 플레이 시각
- 세이브 슬롯별 현재 상태와 플레이 캐릭터
- 수업·모험·미니게임·NPC 만남 등 주요 누적 플레이 카운터
- 확인한 직업 엔딩 목록
- 각 완료 회차의 저장된 엔딩 편지

숨겨진 스탯의 원시 수치, 개인 대화 원문, 비밀번호, Firebase 토큰, 내부 운영 데이터는 표시하지 않습니다.

## 4. 비기능 요구사항

| ID | 항목 | 요구사항 |
|---|---|---|
| NFR-001 | 인증 | 보호 API는 Firebase ID Token을 검증하고 이메일 인증 여부를 확인한다. |
| NFR-002 | 권한 | 기록 조회 API는 인증된 UID 자신의 데이터만 반환한다. |
| NFR-003 | 비밀정보 | Gemini API 키와 Firebase Admin 자격 증명은 클라이언트에 포함하지 않는다. |
| NFR-004 | 개인정보 | AI 입력에는 이메일·비밀번호·토큰 등 편지 생성에 불필요한 개인정보를 넣지 않는다. |
| NFR-005 | 정합성 | 직업 엔딩은 AI 호출 전에 규칙 엔진으로 확정되며 AI 실패가 엔딩·해금·회차 완료를 되돌리지 않는다. |
| NFR-006 | 장애 대응 | Gemini 호출 실패/검증 실패 시 재시도 후 fallback 편지로 엔딩을 완료할 수 있어야 한다. |
| NFR-007 | 저장 | 자동 저장은 정의된 안정 저장 경계에서 수행하고 중간 상태와 완료 상태를 구분한다. |
| NFR-008 | 접근성 | 웹 브라우저에서 데스크톱·모바일의 읽기·선택·기본 조작이 가능해야 한다. |
| NFR-009 | 유지보수 | 모델명·API URL·허용 Origin 같은 환경별 값은 환경변수로 관리하고 비밀값을 Git에 저장하지 않는다. |
| NFR-010 | 추적성 | 소스·문서·요구사항 변경은 GitHub/Git에서 버전 관리한다. |
| NFR-011 | AI 안전 | 어린이의 실제 성격·심리·진로를 진단하거나 존재하지 않은 플레이 기록을 사실처럼 생성하지 않는다. |
| NFR-012 | 범위 관리 | 최종 과제에 필요하지 않은 운영자 CMS·사용자 관리 콘솔은 구현 필수 범위에서 제외한다. |

정량적인 응답 시간·가용성 SLA는 학교 Final Project 프로토타입에 근거 없는 숫자를 만들지 않고, 실제 배포·사용자 테스트 결과가 나온 뒤 측정값으로 기록합니다.

## 5. 시스템 아키텍처

```text
사용자 브라우저
├─ Phaser 3 게임
└─ 읽기 전용 기록 조회 페이지
        ↓
Firebase Authentication
Email/Password + Email Verification
        ↓ Firebase ID Token
FastAPI / Render
├─ 인증·권한 검증
├─ 세이브·Global Meta·플레이 기록 API
├─ 규칙 기반 직업 엔딩 판정
├─ 기록 조회 API (자기 UID만)
└─ 엔딩 편지 Workflow
     ├─ 대표 기록 추출
     ├─ Gemini 입력 구성
     ├─ Gemini API 호출
     ├─ 응답 검증 / fallback
     └─ 엔딩 편지 저장
        ↓
Cloud Firestore
├─ 사용자 메타
├─ Save Slots × 5
├─ Global Meta
├─ 누적 플레이 기록
└─ 엔딩 기록·편지
```

게임 클라이언트와 기록 조회 페이지는 신뢰해야 하는 Firestore 상태를 직접 임의 수정하지 않고 FastAPI를 통해 서버 규칙과 권한 검증을 적용합니다.

## 6. 기술 선택 이유

세부 선정 이유는 `document/10_TECH_STACK.md`를 기준으로 합니다. 요약하면 Phaser 3는 기존 웹 게임/미니게임 자산을 이어 쓰기 위해, FastAPI는 서버 규칙·Firebase Admin·Gemini 연동을 분리하기 위해, Firebase Auth/Firestore는 계정 인증과 계정별 문서형 상태 저장을 위해 사용합니다. Vercel과 Render는 프론트/API 배포 책임을 분리하며, Gemini는 52주 실제 기록을 고정 문구가 아닌 개인화된 서사 보상으로 표현하기 위해 사용합니다.

## 7. 범위 밖 항목

- 운영자용 사용자 전체 검색·정지·권한 변경
- 콘텐츠 CRUD 관리자 CMS
- 운영 통계·BI 대시보드
- 보호자가 별도 계정을 만들고 자녀 계정을 연결하는 가족 계정 시스템
- 실시간 플레이 감시

이 기능들은 향후 확장 가능하지만 Final Project 완료 조건을 위해 구현하지 않습니다.
