# Phaser 3 미니게임 데모 구현 사양서

이 문서는 Coding Agent(Codex)가 읽고 **추가 기획 질문 없이 바로 Phaser 3 데모 구현을 시작할 수 있도록** 작성한 실행 사양서입니다.

기획 원칙과 수업·스탯 연결의 상위 기준은 [수업·미니게임 시스템](06_CLASSES_MINIGAMES.md)을 따릅니다.

---

## 1. 구현 목표

Phaser 3로 여러 미니게임을 한 번에 시험할 수 있는 **독립 실행형 데모 모듈**을 만듭니다.

데모의 첫 화면에는 미니게임 목록이 보이고, 플레이어가 원하는 게임을 눌러 즉시 실행할 수 있어야 합니다. 게임이 끝나면 간단한 결과를 확인한 뒤 목록으로 돌아가 다른 게임을 실행할 수 있어야 합니다.

이 데모의 목적은 최종 LUMIA UI를 만드는 것이 아니라 다음 두 가지를 검증하는 것입니다.

1. 각 미니게임이 `1~3분` 동안 몰입과 사고를 유지할 수 있는가
2. 게임 엔진 담당자가 미니게임 모듈을 기존 Phaser 3 엔진에 쉽게 가져갈 수 있는가

### 필수 UX 흐름

```text
로딩
  ↓
미니게임 목록
  ↓
게임 선택
  ↓
게임 실행
  ↓
결과
  ├─ 다시 하기
  └─ 게임 목록으로
```

## 2. 미니게임 공통 설계 조건

모든 게임은 다음 조건을 만족해야 합니다.

### 2.1 몰입

- 한 판의 목표가 명확해야 합니다.
- 플레이 중 계속 작은 판단을 하게 해야 합니다.
- 단순 반복 클릭이나 자동 진행만으로 해결되면 안 됩니다.
- 게임을 시작하면 현재 판을 끝까지 풀어 보고 싶은 구조를 우선합니다.

### 2.2 플레이 시간

- 목표 플레이 시간: **60~120초**
- 허용 범위: **최소 약 1분, 최대 3분 이내**
- 숙련자가 매우 빠르게 해결하는 것은 허용하지만, 일반적인 난이도에서 20~30초 만에 끝나는 구성을 기본 난이도로 사용하지 않습니다.
- 시간을 채우기 위해 인위적으로 기다리게 하지 않습니다. 퍼즐 수, 보드 크기, 단계 수로 플레이 시간을 확보합니다.

### 2.3 사고 요구

각 게임은 아래 능력 중 최소 하나, 가능하면 둘 이상을 지속적으로 사용해야 합니다.

- 공간 추론
- 경로 계획
- 패턴 인식
- 기억
- 분류
- 규칙 추론
- 가설 수립과 검증
- 선택적 주의와 억제
- 선행 계획

### 2.4 교육 방식

정답 지식을 직접 묻는 퀴즈를 기본으로 하지 않습니다.

```text
권장
룬 회로를 연결한다
→ 공간 추론과 계획을 사용한다

비권장
이 룬의 이름은 무엇인가?
① ... ② ... ③ ...
```

아이에게는 먼저 재미있는 게임이어야 하며, 교육적 경험은 **게임 규칙 안에서 자연스럽게 발생**해야 합니다.

## 3. 구현 환경 기준

### 3.1 Phaser

- 엔진: **Phaser 3**
- 현재 프로토타입 문서의 기준 버전: **Phaser 3.90.0**
- 구현 시 기존 엔진 작업 영역에 Phaser 3 환경이 이미 있으면 그 환경을 우선 사용합니다.
- 현재 저장소에서 별도 엔진 scaffold가 없다면 독립 데모는 `phaser@3.90.0`을 기준으로 만듭니다.

### 3.2 프로토타입에서 확인된 참고 구조

`prototype/`은 읽기 전용 기준물로 참고하며 수정하지 않습니다.

현재 프로토타입은 다음 특징을 가지고 있습니다.

- Phaser를 사용하는 장면은 ES module로 분리되어 있음
- `prototype/adventure.mjs`에서 Phaser Scene을 만들고 외부 UI와 lifecycle을 연결함
- `prototype/puzzle.mjs`는 퍼즐 판정을 렌더링과 분리한 **순수 로직 모듈**임
- Node 정적 서버로 프로토타입을 실행하는 구조가 있음
- 프로토타입 README에는 Phaser 3.90.0과 `vendor/phaser.min.js`가 명시되어 있으나, 현재 작업공간에서는 `package.json`과 `vendor/phaser.min.js`가 확인되지 않음

따라서 새 데모에서 프로토타입의 파일 배치를 그대로 복사하지 않습니다. **로직과 Phaser Scene을 분리하는 구조만 적극 재사용**합니다.

### 3.3 독립 데모 scaffold 결정 규칙

Codex가 구현을 시작할 때 다음 순서로 판단합니다.

1. `engine/`에 Phaser 3 package/build 환경이 이미 존재하면 해당 환경 안에서 **격리된 미니게임 데모 모듈**을 만듭니다.
2. Phaser 환경이 없다면 `engine/minigame-demo/`에 독립 실행 가능한 최소 scaffold를 만듭니다.
3. 독립 scaffold가 필요할 때는 ES module 기반 Phaser 3 프로젝트를 사용하며, 번들러는 데모 실행에 필요한 최소 구성만 둡니다. 다른 LUMIA 코드에 의존하지 않습니다.
4. `prototype/`과 `lumia/`는 수정하지 않습니다.

## 4. 모듈화 요구사항

게임 엔진 담당자가 각 게임을 **Scene 단위로 가져갈 수 있어야 합니다.**

권장 구조:

```text
engine/minigame-demo/
├── index.html
├── package.json
├── src/
│   ├── main.js
│   ├── config.js
│   ├── scenes/
│   │   ├── MenuScene.js
│   │   └── ResultScene.js
│   ├── minigames/
│   │   ├── index.js
│   │   ├── shared/
│   │   │   ├── BaseMinigameScene.js
│   │   │   ├── constants.js
│   │   │   └── rng.js
│   │   ├── rune-circuit/
│   │   │   ├── RuneCircuitScene.js
│   │   │   ├── logic.js
│   │   │   └── levels.js
│   │   ├── treasure-search/
│   │   ├── rune-link/
│   │   ├── target-training/
│   │   ├── rune-block-push/
│   │   ├── mirror-magic/
│   │   └── rule-path/
│   └── ui/
└── tests/
```

폴더명은 구현 중 약간 바뀌어도 되지만 다음 원칙은 유지합니다.

### 필수 구조 원칙

- **게임 규칙/판정 로직과 Phaser 렌더링을 분리**합니다.
- `logic.js`는 가능한 한 DOM과 Phaser에 의존하지 않는 순수 함수로 작성합니다.
- 랜덤 게임은 seed를 받을 수 있게 하여 재현 가능한 테스트가 가능해야 합니다.
- 게임 Scene이 LUMIA의 저장 데이터, localStorage, 캐릭터 상태에 직접 접근하면 안 됩니다.
- 게임 결과는 공통 result object로 외부에 전달합니다.
- 각 게임은 자신의 이벤트 listener, timer, tween을 종료 시 정리해야 합니다.
- 데모 전용 메뉴와 결과 화면은 미니게임 로직 내부에 넣지 않습니다.

## 5. 공통 미니게임 인터페이스

각 미니게임은 최소 다음 metadata를 registry에 제공합니다.

```js
{
  id: 'rune-circuit',
  title: '룬 회로',
  className: '마법훈련',
  stat: '마법',
  description: '룬을 돌려 마력의 시작점과 마법진을 연결한다.',
  expectedDuration: '1~2분',
  scene: RuneCircuitScene
}
```

Scene 시작 시 받을 수 있는 표준 데이터:

```js
{
  difficulty: 1,
  seed: 'demo-seed',
  maxDurationMs: 180000
}
```

게임 완료 결과 형식:

```js
{
  gameId: 'rune-circuit',
  outcome: 'success', // success | timeout | quit
  score: 820,
  durationMs: 83420,
  difficulty: 1,
  seed: 'demo-seed',
  metrics: {
    attempts: 14,
    mistakes: 3,
    roundsCleared: 3
  }
}
```

### 결과 전달

게임 내부에서 LUMIA 스탯을 직접 올리지 않습니다.

미니게임은 result만 반환하고, 최종 엔진이 다음처럼 해석할 수 있어야 합니다.

```text
미니게임 결과
   ↓
LUMIA 엔진/수업 시스템
   ↓
스탯 증가량 계산
   ↓
저장
```

권장 이벤트 이름:

```text
minigame:complete
minigame:quit
```

이벤트 방식은 실제 엔진 구조에 맞춰 adapter로 바꿀 수 있지만 **게임이 직접 전역 상태를 수정하지 않는 원칙**은 유지합니다.

## 6. 데모 메뉴 요구사항

첫 화면에서 모든 구현 대상 게임을 확인할 수 있어야 합니다.

각 게임 카드에는 다음을 표시합니다.

- 게임 이름
- 연결 수업
- 연결 스탯
- 한 줄 규칙 설명
- 사용하는 사고 능력
- 예상 플레이 시간
- `플레이` 버튼

데모 단계에서는 잠금, 캐릭터, 주간 일정, 체력 시스템을 구현하지 않습니다.

### 공통 게임 HUD

게임 화면에는 최소 다음을 둡니다.

- 게임명
- 현재 진행 상황 또는 남은 시간
- 현재 규칙/목표
- 다시 시작
- 게임 목록으로 돌아가기

게임 목록으로 돌아갈 때 현재 게임의 Scene과 입력을 완전히 종료합니다.

## 7. 이번 데모의 필수 구현 게임 7종

현재까지 논의한 게임 중 최신 기준인 `몰입 / 1분 이상 지속 가능 / 사고 요구`에 가장 잘 맞는 **7종을 1차 구현 대상**으로 합니다.

### 7.1 룬 회로 — 파이프 연결 퍼즐

| 항목 | 내용 |
|---|---|
| ID | `rune-circuit` |
| 수업 | 마법훈련 |
| 스탯 | 마법 |
| 핵심 사고 | 공간 추론, 경로 계획, 오류 수정 |
| 목표 시간 | 60~120초 |

#### 규칙

- 시작 룬에서 도착 마법진까지 하나의 유효한 마력 경로를 만듭니다.
- 타일을 눌러 90도씩 회전합니다.
- 시작점과 도착점은 회전할 수 없습니다.
- 연결된 구간은 즉시 빛나게 표시합니다.
- 모든 타일을 사용할 필요는 없습니다.

#### 난이도

기존 프로토타입의 3×3 퍼즐은 참고 로직으로만 사용합니다. 데모의 기본 난이도는 그것보다 길게 플레이할 수 있어야 합니다.

권장:

```text
Round 1: 4×4
Round 2: 5×5 + 불필요 타일
Round 3: 5×5 + 고정 타일 또는 반드시 통과할 룬
```

각 판은 생성 후 실제 해답이 존재하는지 검증해야 합니다. 랜덤 생성이 복잡하면 먼저 검증된 stage 데이터를 사용합니다.

---

### 7.2 숨겨진 보물 — 추론형 땅 파기

| 항목 | 내용 |
|---|---|
| ID | `treasure-search` |
| 수업 | 탐사 수업(제안명) |
| 스탯 | 탐험 |
| 핵심 사고 | 공간 추론, 가설 수립, 탐색 범위 축소 |
| 목표 시간 | 60~120초 |

#### 규칙

- 격자 어딘가에 보물이 숨겨져 있습니다.
- 플레이어가 칸을 선택해 조사하면 보물과의 거리 또는 방향에 대한 단서를 얻습니다.
- 단서를 바탕으로 다음 조사 위치를 정합니다.
- 단순 랜덤 운으로 찾는 게임이 되지 않도록 **모든 조사 결과가 정보**를 줘야 합니다.

#### 기본 보드

- 7×7 또는 8×8
- 한 라운드당 조사 횟수 제한
- 한 세션에 2~3개의 보물 라운드

#### 단서 예시

- 매우 가까움 / 가까움 / 멀음
- 이전 조사보다 가까워짐 / 멀어짐
- 북쪽·동쪽 등 큰 방향 힌트

숫자 계산 문제처럼 보이기보다 시각 효과와 짧은 텍스트로 거리감을 보여 줍니다.

---

### 7.3 기억의 서고 — 사천성형 짝 연결

| 항목 | 내용 |
|---|---|
| ID | `rune-link` |
| 수업 | 고대학 수업(제안명) |
| 스탯 | 지식 |
| 핵심 사고 | 시각 탐색, 기억, 제거 순서 계획 |
| 목표 시간 | 60~150초 |

#### 규칙

- 같은 문양 두 개를 선택해 제거합니다.
- 두 타일은 **최대 2번 꺾이는 경로**로 연결할 수 있을 때만 제거됩니다.
- 단순 메모리 매칭이 아니라 어떤 짝을 먼저 제거해야 다음 경로가 열리는지 판단하게 합니다.
- 연결 가능한 쌍이 없으면 deadlock을 감지해 자동 shuffle합니다. shuffle은 점수에 작은 불이익만 주고 게임을 막지 않습니다.

#### 보드 권장

- 8×6 전후
- 약 20~24쌍
- 라운드 1회가 기본 세션

아트가 없어도 색·기호 조합으로 구현 가능해야 합니다.

---

### 7.4 표적 훈련 — 규칙 판단형 반응 게임

| 항목 | 내용 |
|---|---|
| ID | `target-training` |
| 수업 | 검술훈련 |
| 스탯 | 솜씨 |
| 핵심 사고 | 선택적 주의, 작업 기억, 억제, 반응 |
| 목표 시간 | 약 90초 |

기존의 `좋은 아이템 받기 / 나쁜 아이템 피하기`만으로는 사고 요구가 약하므로 **규칙이 바뀌는 판단 게임**으로 구현합니다.

#### 예시 규칙

```text
Wave 1
파란 원 → 베기
빨간 표적 → 피하기

Wave 2
삼각형 → 막기
원형 → 베기
빨간색 → 무조건 피하기
```

#### 조작

- `베기`
- `막기`
- 아무 행동도 하지 않기

마우스/터치 버튼을 기본으로 하고 키보드 단축키를 보조 입력으로 제공합니다.

#### 세션

- 3개 wave
- wave당 약 25~30초
- wave가 바뀔 때 규칙 카드가 2~3초 동안 명확하게 표시됨
- 규칙은 플레이 중에도 항상 작은 형태로 확인 가능

순수 반사신경 게임이 되지 않도록 **색 + 모양 + 현재 규칙**을 함께 판단하게 합니다.

### 7.5 룬 블록 밀기 — Sokoban형 공간 퍼즐

| 항목 | 내용 |
|---|---|
| ID | `rune-block-push` |
| 수업 연결 | 고대학 또는 실기 계열 후보. 데모에서는 수업 미확정 표시 |
| 핵심 사고 | 선행 계획, 공간 추론, 실수 예측 |
| 목표 시간 | 60~180초 |

#### 규칙

- 플레이어가 룬석을 밀어 지정된 마법진 위에 놓습니다.
- 룬석은 **밀 수 있지만 당길 수 없습니다.**
- 막힌 위치로 잘못 밀면 해결할 수 없을 수 있으므로 먼저 생각해야 합니다.

#### 데모 범위

- 3개 hand-authored stage
- Stage 1: 상자 1~2개
- Stage 2: 상자 2개
- Stage 3: 상자 2~3개 + 좁은 통로
- `Undo`와 `Restart` 제공

랜덤 생성기는 1차 데모 범위가 아닙니다. 먼저 좋은 문제 3개를 검증합니다.

### 7.6 거울 마법 — 빛 반사 퍼즐

| 항목 | 내용 |
|---|---|
| ID | `mirror-magic` |
| 수업 | 마법훈련 |
| 스탯 | 마법 |
| 핵심 사고 | 경로 예측, 회전, 공간 추론 |
| 목표 시간 | 60~150초 |

#### 규칙

- 빛은 직선으로 진행합니다.
- 플레이어가 거울을 회전해 빛을 목표 룬으로 보냅니다.
- 거울은 `/` 또는 `\` 방향을 가집니다.
- 거울을 누르면 즉시 빛의 경로를 다시 계산하고 화면에 보여 줍니다.

#### 데모 범위

- 3개 stage
- Stage 1: 목표 1개
- Stage 2: 거울 수 증가 + 장애물
- Stage 3: 반드시 특정 룬을 통과해야 성공

분광기, 색 혼합, 광선 분할은 후속 확장으로 미룹니다.

### 7.7 조건형 길 찾기 — 규칙이 있는 탐사 경로

| 항목 | 내용 |
|---|---|
| ID | `rule-path` |
| 수업 | 탐사 수업(제안명) |
| 스탯 | 탐험 |
| 핵심 사고 | 경로 계획, 조건 관리, 선행 판단 |
| 목표 시간 | 60~150초 |

일반 미로처럼 길만 찾는 게임은 너무 쉬울 수 있으므로 **경로 조건**을 둡니다.

#### 조건 예시

- 열쇠를 먼저 획득해야 문을 통과할 수 있음
- 같은 색 발판을 연속으로 밟을 수 없음
- 제한된 마력 안에서 목적지 도달
- 특정 룬을 하나 이상 지나야 함

#### 권장 조작

바로 캐릭터를 이동시키기보다 먼저 경로를 계획하게 합니다.

```text
인접 칸 선택
→ 계획 경로 생성
→ Undo 가능
→ 실행
→ 조건 충족 여부 확인
```

3개 stage를 사용하고 각 stage는 규칙을 하나씩 추가합니다.

## 8. 1차 데모에서 제외하는 아이디어

아래 아이디어는 폐기하지 않지만 **이번 필수 구현에는 포함하지 않습니다.**

| 게임 | 상태 | 이유 |
|---|---|---|
| 마법 무대 리듬 게임 | 보류 | 표현력 테마에는 맞지만 최신 기준의 `적당한 사고 요구`가 상대적으로 약함 |
| 마법진 순서 복원 | 후보 | 논리 퍼즐로 좋지만 7종 구현 후 지식 계열 확장에 사용 |
| 마법 가방 정리 | 후보 | 공간 퍼즐로 유효하지만 룬 블록 밀기와 역할 일부 중복 |
| 숨은 규칙 찾기 | 후보 | 높은 교육 가치가 있으나 규칙 설명 UX를 별도 설계해야 함 |
| 무게 맞추기 | 후보 | 관계·수량 추론용으로 좋지만 테마와 난이도 추가 설계 필요 |

표현력 수업용 게임은 현재 **미해결 과제**로 남깁니다. 표현력에 맞으면서도 퍼즐 깊이를 가진 별도 게임을 이후 설계합니다.

## 9. 공통 난이도 원칙

난이도는 단순히 타이머를 줄이는 방식보다 **생각해야 할 상태 수를 늘리는 방식**으로 올립니다.

권장:

- 보드 크기 증가
- 선택지 증가
- 장애물 추가
- 반드시 지켜야 할 조건 추가
- 여러 단계 계획 필요
- 불필요한 오브젝트 추가

비권장:

- 화면만 지나치게 빠르게 만들기
- 입력 시간을 과도하게 짧게 만들기
- 작은 터치 대상 사용
- 실패 시 처음부터 긴 구간을 반복시키기

기본 difficulty 값은 `1`로 시작합니다. 이번 데모에서 difficulty 선택 UI는 필수가 아니며, 각 게임 안에서 2~3단계가 자연스럽게 상승하면 충분합니다.

## 10. 시각/에셋 원칙

이번 데모는 게임성 검증이 목적이므로 새로운 최종 아트를 요구하지 않습니다.

- Phaser `Graphics`, `Text`, 간단한 기하 도형을 적극 사용합니다.
- 기존 `asset/` 파일을 사용해도 되지만 게임 로직이 특정 이미지 없이는 동작하지 않게 만들지 않습니다.
- 색상만으로 상태를 구분하지 말고 모양/기호도 함께 사용합니다.
- 룬, 마력, 아르카디아라는 판타지 테마는 유지하되 최종 디자인 작업처럼 과도하게 꾸미지 않습니다.
- 최종 엔진 담당자가 에셋을 교체하기 쉽게 texture key 또는 theme mapping을 한 곳에 모읍니다.

## 11. 입력과 반응형

데모는 데스크톱 브라우저를 우선하되 pointer 입력을 사용하여 터치에서도 기본 플레이가 가능하게 합니다.

- 주요 조작은 클릭/터치로 완료 가능해야 합니다.
- 키보드는 보조 입력입니다.
- 드래그가 필수인 게임은 가능하면 클릭 기반 대체 입력도 제공합니다.
- UI 버튼은 모바일에서도 누를 수 있는 크기로 만듭니다.
- 고정 좌표만 사용하지 말고 `this.scale.width / height`를 기준으로 주요 보드를 중앙 정렬합니다.
- resize 시 게임이 깨지지 않아야 합니다.

독립 데모 shell은 기준 논리 해상도 `1280×720`을 사용해도 되며 Phaser Scale의 `FIT + CENTER_BOTH` 방식으로 시작할 수 있습니다. 실제 엔진에 가져갈 Scene 내부에서는 해상도에 과도하게 의존하지 않습니다.

## 12. 점수와 결과

이번 데모의 점수는 게임성 확인용입니다. LUMIA 최종 성장 수치와 직접 연결하지 않습니다.

공통적으로 다음 요소를 조합할 수 있습니다.

```text
기본 성공 점수
+ 남은 시간
+ 적은 행동 수 / 좋은 효율
- 힌트 또는 shuffle
- 잘못된 입력
```

하지만 **정답을 못 맞혔다고 스탯을 감소시키는 개념은 구현하지 않습니다.**

결과 화면에는 다음 정도만 표시합니다.

- 성공 / 시간 종료
- 점수
- 플레이 시간
- 게임별 대표 지표 1~3개
- 다시 하기
- 목록으로

## 13. 테스트 요구사항

게임마다 최소한 핵심 로직의 자동 테스트를 작성합니다.

### 공통

- 같은 seed가 같은 초기 상태를 만드는지
- 결과 이벤트가 한 판에 한 번만 발생하는지
- restart 시 이전 timer/listener가 남지 않는지

### 룬 회로

- 회전 4회 후 원상복귀
- 경계 밖 연결 금지
- 생성/등록 stage에 해답 존재
- 시작점에서 도착점 연결 판정

### 보물 찾기

- 거리/방향 힌트가 실제 보물 위치와 일치
- 같은 칸 중복 조사 처리
- 조사 횟수 종료 처리

### 사천성형 연결

- 0/1/2회 꺾임 연결 판정
- 3회 이상 꺾임 거부
- 다른 타일 통과 금지
- deadlock 감지

### 표적 훈련

- 현재 rule에 따라 베기/막기/무시 판정
- wave 변경 시 rule 갱신
- 동일 입력 중복 채점 방지

### 룬 블록 밀기

- 벽 통과 금지
- 룬석 당기기 불가
- 룬석 뒤가 막혀 있으면 이동 불가
- 모든 목표 점유 시 성공

### 거울 마법

- `/`, `\` 반사 방향 판정
- 장애물에서 광선 종료
- 무한 반사 loop 감지 및 종료
- 목표 도달 판정

### 조건형 길 찾기

- 인접하지 않은 칸 추가 금지
- 열쇠/문 조건
- 색/에너지 규칙 판정
- 실행 전 경로 수정 가능
