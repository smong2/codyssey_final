# 이벤트 대화 시퀀스 계약

이 문서는 메인·지역·NPC 이벤트에서 사용하는 **미리 작성된 캐릭터별 대화**의 콘텐츠 작성과 재생 규칙을 정의한다. 여기서 **스토리 회차**는 NPC·지역 스토리의 1화·2화 같은 **진행 단계** 또는 메인 스토리의 한 이벤트 단위를 뜻한다. 52주를 끝내고 다시 시작하는 플레이 회차(`runNumber`)와 다르다.

이 문서는 대사 원고가 아니다. 실제 사건·등장인물·이미지 사용 지시는 `story/main/`, `story/location/`, `story/npc/`의 해당 스토리 원고에 두고, 클라이언트가 조회할 시퀀스는 [SQLite 대화 테이블](../../backend/database/sqlite/SCHEMA.md)에 적재한다. 현재 원고와 자원에 없는 대사·이미지를 이 문서로 확정하지 않는다.

## 1. 어떤 대화를 준비하는가

1. 서버가 기존 [이벤트 발생 규칙](02_STATS_EVENTS_ENDINGS/02_EVENTS.md)으로 메인·지역·NPC 이벤트와 스토리 진행 단계를 결정한다.
2. `(gameDataVersion, storyId, stepNo, eventId, playerCharacterId)`에 맞는 **사전 작성 시퀀스 한 개**를 선택한다. `eventId`는 해당 스토리 단계에 속해야 한다.
3. 캐릭터 32명은 같은 사건을 겪더라도 말투, 질문, 입학 동기·관심사, 상대 NPC의 반응이 다를 수 있다. **메인·지역 이벤트의 각 단계에는 32명 각각의 대화 시퀀스**를 준비한다. 공통 줄거리는 유지해도 실제 대사와 상대 반응을 캐릭터에 맞춰 작성한다.
4. NPC 이벤트도 참여 가능한 캐릭터마다 시퀀스를 준비한다. 대상 NPC가 플레이 가능한 캐릭터이고 현재 플레이 캐릭터와 같으면 기존 규칙대로 자기 자신과의 NPC 조우를 제외한다. 이 경우 해당 조합의 시퀀스는 요구하지 않는다. 대상 NPC가 플레이 캐릭터와 겹치지 않으면 32명 모두 필요하다.
5. 이야기에 대화 외 조사·퍼즐·이동이 있다면 해당 상호작용은 기존 이벤트/스토리 흐름에서 처리한다. 이 문서는 그 안의 대화 장면 순서와 선택·이미지 표현을 맡는다.

> 위 32개는 플레이 시점에 생성하는 문장이 아니라 **콘텐츠 출시 전에 작성·검수할 변형 원고**다. 아직 원고가 없는 이벤트/캐릭터 조합은 완성으로 표시하거나 임의의 공통 대사로 대체하지 않는다. 메인 스토리의 사건·결말은 공통으로 유지하되, 기존 시나리오 초안의 `짧은 캐릭터별 맥락` 제안보다 **대사 원고의 캐릭터별 차이를 넓힌 최신 사용자 결정**을 적용한다. 실제 메인 원고와의 문장·배역 조정은 스토리 작성 영역에서 후속 검토한다.

### 1.1 회차 단위 동적 배역 `storyCast`

메인·Location Story의 일부 학생 역할은 특정 학생 한 명을 하드코딩하지 않고 **주인공 선택 직후 회차 단위로 확정한 배역 맵**을 사용한다. 역할별 후보와 우선순위는 `story/main/MAIN_STORY_PRODUCTION.md`, `story/location/LOCATION_STORY_PRODUCTION.md`를 원본으로 한다.

```text
캐릭터 선택 확정
→ 역할별 후보에서 playerCharacterId 제외
→ 이미 다른 핵심 역할에 배정된 학생 제외
→ 역할별 첫 사용 가능 학생 선택
→ activeRun.storyCast 저장
→ 해당 회차 종료까지 같은 배역 유지
```

주요 역할 예:

- `MAIN_GUIDE_STUDENT`
- `MAIN_GREENHOUSE_STUDENT`
- `MAIN_GREENHOUSE_TRAPPED`
- `MAIN_CLOCK_STUDENT`
- `MAIN_TRAINING_STUDENT`
- `MAIN_TRAINING_WITNESS`
- `MAIN_FESTIVAL_LEAD`
- `LOC_GREENHOUSE_STUDENT`

`LOC_GREENHOUSE_STUDENT`는 주인공뿐 아니라 `MAIN_GREENHOUSE_STUDENT`와도 다른 학생을 우선한다. `MAIN_TEACHER`는 발렌티누스로 고정하며 32인 학생 캐스팅 대상이 아니다.

주인공 캐릭터의 **해금 여부는 조력 NPC 등장 가능 여부와 분리**한다. 주인공으로 아직 잠긴 학생도 스토리의 조력 학생으로는 등장할 수 있다.

대화 원고에서 동적 역할을 가리킬 때 `speaker_ref`는 `ROLE:<roleId>` 형식을 사용할 수 있다. 예: `ROLE:MAIN_GREENHOUSE_STUDENT`. 재생 시에는 현재 `activeRun.storyCast[roleId]`의 실제 캐릭터 ID로 변환해 이름·스프라이트·말투 자원을 표시한다. 고정 NPC는 기존처럼 실제 NPC ID를 직접 사용한다.

## 2. 원고 한 편의 필수 구조

각 `(스토리, 단계, 플레이 캐릭터)` 시퀀스는 시작 노드부터 종료 노드까지 순서대로 한 노드씩 노출한다. 분기 선택 이후에는 해당 선택의 상대 반응을 보여 준 뒤, 앞선 선택을 전제하지 않는 중립적인 공통 대화로 합류하는 것을 기본으로 한다.

```text
시작 → 대사 → (필요 시 이미지) → 선택지
                              ├─ 선택 A → 상대의 A 반응 ─┐
                              └─ 선택 B → 상대의 B 반응 ─┤
                                                       ↓
                                           중립적인 공통 대사 → 종료
```

- **필수 선택:** 각 캐릭터별 시퀀스에는 최소 한 개의 선택 노드가 있어야 하고, 선택 노드마다 고를 수 있는 선택지가 최소 두 개 있어야 한다. 실제 플레이 경로가 어느 분기를 지나도 최소 한 번은 선택하도록 작성한다.
- **상대 반응:** 선택 결과가 바로 공통 문장으로 합쳐지지 않도록, 각 선택지 뒤에는 실제 대화 상대의 짧은 개별 반응을 넣는다. 플레이 캐릭터에 따라 상대의 말투·감정·답변도 조정한다.
- **합류 문장:** 긍정·부정 등 어떤 답을 골라도 모순되지 않는 내용으로 쓴다. 이후 선택을 다시 언급해야 하면 `eventFlags`로 구분해 후속 이벤트에서 처리한다.
- **마무리:** 모든 분기는 정상 종료 노드에 도달해야 한다. 선택에 오답 페널티나 진행 불능을 두지 않는 기존 이벤트 규칙을 유지한다.
- **식별자:** `eventId`, `characterId`, `choiceId`, `nodeId`는 같은 마스터 버전 안에서 안정적으로 유지한다. `choiceId`는 화면 문구와 별개인 의미 ID이며, 서버 결과 처리와 엔딩 기억의 최소 참조에 사용한다.

### 이미지 노출

이미지의 **사용 여부·자원·장면 위치는 해당 `story/` 원고에 명시**한다. 명시된 장면만 대화 시퀀스의 이미지 노드 또는 이미지가 붙은 대사 노드로 옮긴다. 클라이언트는 그 노드에 도달할 때 자원을 보여 준다. 여러 이미지는 각 노드의 순서로 표시할 수 있다. 대화 데이터가 없는 이미지를 임의로 생성하거나, 원고에 없는 이미지를 자동 노출하지 않는다. 자원 경로와 실제 표시 가능 여부는 콘텐츠 적재 전에 확인한다.

## 3. 재생과 저장 경계

```text
이벤트 조건 판정·선정 (서버)
→ 선택 캐릭터의 대화 시퀀스 조회 (로컬 SQLite 마스터 사본)
→ 시작 노드부터 대사·이미지를 하나씩 표시
→ 선택지에서 choiceId 선택
→ 해당 상대 반응 → 공통 대화 합류 → 종료
→ 결과·스토리 진행·필요한 선택 플래그를 서버가 검증
→ Firestore 안정 저장 성공 후 이벤트 완료
```

노드 위치를 Firestore에 매 줄 저장하지 않는다. 장면 중간에 종료하면 [기존 이벤트 저장 경계](02_STATS_EVENTS_ENDINGS/02_EVENTS.md#41-대화-장면-저장-경계)에 따라 완료 결과가 없으며, 다음 정상 진입은 마지막 확정 체크포인트에서 판단한다. 로컬 UI가 시퀀스 위치를 잠시 기억하더라도 서버의 이벤트 완료 근거가 되지 않는다.

선택 원문과 전체 대화문을 사용자별로 장기 저장하지 않는다. 장면 종료 때 서버는 필요한 효과와 `storyProgress`·`eventFlags`를 저장하고, 중요한 선택만 기존 `representativeChoices`의 `eventId / choiceId / week` 참조로 남긴다. 관리자 통계도 플레이어 SQLite 대화 캐시에서 수집하지 않는다.

## 4. SQLite 데이터 계약

[두 번째 마이그레이션](../../backend/database/sqlite/002_dialogue_sequences.sql)은 다음 읽기용 마스터 테이블을 추가한다.

| 테이블 | 한 행의 의미 | 주요 키 |
|---|---|---|
| `dialogue_sequences` | 스토리 단계·이벤트·플레이 캐릭터의 대화 한 편과 시작 노드 | `version + story_id + step_no + character_id` |
| `dialogue_nodes` | 대사(`LINE`), 이미지(`IMAGE`), 선택 지점(`CHOICE`), 종료(`END`) 한 칸. NPC 화자는 고정 ID 또는 `ROLE:<roleId>`를 사용할 수 있음 | 시퀀스 키 + `node_id` |
| `dialogue_options` | 선택 문구와 해당 선택의 첫 반응 노드 | 시퀀스 키 + `choice_node_id + choice_id` |

`dialogue_nodes.next_node_id`는 선택을 제외한 다음 노드를 가리킨다. `dialogue_options.response_node_id`는 선택 직후의 반응으로 진입한다. `speaker_kind`는 `PLAYER`·`NPC`·`NARRATOR`를 구분하고, `speaker_ref`는 고정 NPC 화자 식별자 또는 `ROLE:<roleId>` 동적 배역 참조다. 동적 배역은 반드시 현재 회차 `storyCast`에서 실제 학생 ID로 해석되어야 하며, 미해결 role을 임의 NPC로 대체하지 않는다. 실제 선택 문구는 캐릭터별로 다를 수 있으며, 같은 의미의 `choiceId`를 공유할 수 있다. 기존 `story_choices`는 이벤트 수준 선택 의미·다음 이벤트 연결에 사용하고, 실제 화면 문구와 그 직후 대화 분기는 `dialogue_options`가 담당한다. 콘텐츠 적재 시 각 옵션의 `choiceId`가 해당 이벤트의 `story_choices`에 등록됐는지 확인한다.

## 5. 콘텐츠 적재 전 검수 기준

새 마스터 버전을 활성화하기 전에 다음을 **스토리 원고와 SQLite 적재 결과 양쪽**에서 확인한다. SQL의 행 단위 `CHECK`와 외래 키만으로는 모든 경로와 캐릭터 커버리지를 증명할 수 없으므로, 적재기/검증기가 이 항목을 검사해야 한다.

1. 각 메인·지역 스토리 단계의 시퀀스가 플레이 캐릭터 32명 모두에게 존재한다.
2. NPC 스토리 단계는 자기 자신과의 조우만 제외하고 나머지 참여 가능 캐릭터 모두에게 존재한다.
3. 각 시퀀스의 시작 노드가 존재하고, 모든 `next_node_id`·`response_node_id`가 같은 시퀀스 안의 노드를 가리킨다.
4. **시작점에서 실제로 도달 가능한 모든 경로**에 최소 한 번의 선택이 있고, 각 선택 노드에 최소 두 옵션이 있다. 선택 후 상대 반응이 존재하며 모든 분기가 종료에 도달한다.
5. 이미지가 있는 노드는 해당 스토리 원고의 이미지 지시와 일치하고 실제 자원 경로가 존재한다.
6. 선택의 `choiceId`가 같은 이벤트의 `story_choices` 의미 정의와 일치한다. 선택 결과·분기 문장·공통 합류 문장이 플레이 캐릭터와 선택 내용에 모순되지 않는다.
7. 다른 마스터 버전이나 다른 캐릭터의 노드를 참조하지 않으며, 샘플 실행에서 캐릭터별 첫 대사·선택·상대 반응·이미지·종료가 의도한 순서로 표시된다.
8. `ROLE:<roleId>` 화자가 있는 시퀀스는 모든 플레이 캐릭터 32명에 대해 회차 시작 캐스팅이 성공하고, 주인공 자신이 자기 상대역으로 배정되지 않으며, `LOC_GREENHOUSE_STUDENT`가 같은 회차의 `MAIN_GREENHOUSE_STUDENT`와 중복되지 않는지 검증한다.

이 검수는 **시퀀스 데이터가 실제로 작성·적재된 뒤** 수행한다. 이번 DB 마이그레이션은 테이블만 만들며 32명분 원고나 이미지 자원을 생성하지 않는다.
