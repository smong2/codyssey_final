# LUMIA Final Project 기획서

이 문서는 LUMIA를 시작한 문제의식, 어린이에게 제공할 경험, AI 활용 방식과 제출 범위를 설명하는 WBS 10.1.1의 기획서입니다. 세부 게임 규칙은 `document/content/`, 기능 우선순위는 `document/12_REQUIREMENTS_ARCHITECTURE.md`, 기술 구현 기준은 `document/10_TECH_STACK.md`, 역할 경계는 `document/05_TEAM_ROLES.md`를 우선합니다. 범위·일정·담당의 작업 단위는 GitHub WBS를 참고하되, 이 기획서와 확정된 요구 명세에 어긋나는 오래된 이슈 문구를 제품 결정으로 사용하지 않습니다.

## 1. 프로젝트 문제 정의

LUMIA는 **아이들이 다른 사람의 마음을 이해하고 배려하며 함께 문제를 풀어 보는 경험을 어떻게 만들 수 있을까**, **보호자가 아이의 생각을 알고 대화를 시작할 실마리를 어떻게 얻을 수 있을까** 하는 고민에서 출발했습니다. 어린이의 사회적 관계와 배려 경험이 부족해지는 것은 아닐까 하는 미디어의 문제 제기를 접한 것이 계기였습니다. 이를 모든 어린이에 대한 진단이나 단정으로 삼지 않고, 게임에서 탐색할 질문으로 둡니다.

그 질문에 답하기 위해 아르카디아라는 가상의 생활 세계를 만들었습니다. 어린이는 배려·협력·선의를 각기 다른 방식으로 보여 주는 인물들과 관계를 맺고, 사건 앞에서 스스로 관찰하고 선택합니다. 어떤 말과 행동에 마음이 움직이는지, 서로 다른 관점을 만났을 때 무엇을 선택하는지 살필 수 있는 경험을 지향합니다. 게임은 선택의 선악을 채점하거나 아이의 성격을 판단하지 않고, 인물과 세계의 반응으로 선택의 결과를 보여 줍니다.

52주에 걸친 경험이 마지막에 한 사람의 이야기로 돌아오도록, 게임 규칙이 미래 직업 엔딩을 먼저 확정하고 생성형 AI가 실제 플레이 기록을 바탕으로 개인화된 회고 편지를 씁니다. 고정 엔딩만으로 표현하기 어려운 활동·만남·선택의 조합을 이번 플레이어만의 미래 이야기로 연결하는 것이 LUMIA의 해결 방식입니다.

## 2. 대상 사용자와 제공 가치

- 주 대상: 약 **9~11세 어린이**
- 플레이 맥락: 서로 다른 성격과 배경을 지닌 학생 캐릭터 32명 중 주인공을 선택하고, 웹에서 52주 동안 수업·모험·휴식, 사건·NPC 교류, 수집·해금을 이어 갑니다. 그 과정에서 수십 번의 선택과 여러 인물의 관점을 만납니다.
- 어린이에게 주는 가치: 이상적인 세계의 정답을 주입하기보다, 주인공으로서 관계를 맺고 배려·협력의 여러 모습을 경험하며 스스로 생각할 공간을 제공합니다. 선택은 도덕 점수 대신 인물과 세계의 변화로 돌아오고, 누적된 경험은 마지막에 개인화된 미래 이야기로 이어집니다.
- 보호자를 위한 장기 비전: 아이의 마음을 단정하거나 감시하는 보고서가 아니라, 플레이에서 드러난 관심과 선택을 바탕으로 부모·자녀가 대화를 시작할 단서를 제공하고자 합니다. AI 활동 요약·보고서의 조회와 보호자에게 전달하는 방식은 제출 후 별도로 설계합니다.

제출판의 관리자 콘솔은 보호자용 화면이 아니라 **LUMIA 제작·운영팀의 운영 화면**입니다. 승인된 운영자가 회원·플레이 기록과 집계 통계를 조회하고 제한된 전역 성장 보상 배율을 조정합니다. 사용자별 저장값 직접 수정이나 실시간 감시는 제공하지 않습니다.

## 3. 요구사항 기술 적용 내용

LUMIA의 핵심 AI 기능은 **개인화 엔딩 편지**입니다.

AI는 52주 동안 각기 다른 활동·만남·선택을 한 어린이에게 같은 고정 문장을 반복하지 않고, **이번 플레이가 어떤 미래 이야기로 이어지는지** 표현합니다. 따라서 AI는 게임 밖에 덧붙이는 기능이 아니라, 긴 플레이의 결과를 자기 이야기로 돌려주는 핵심 보상을 완성합니다.

AI는 직업을 결정하거나 플레이어의 성격을 진단하지 않습니다. 게임 시스템이 확정한 직업과 실제 플레이 기록을 자연어로 해석하는 역할만 담당합니다. 작가의 고정 질문 `무엇을 지켰니?`에도 AI가 하나의 정답을 대신 제시하지 않습니다.

AI 입력에는 확정된 직업, 현재 회차의 최종 스탯, 활동 횟수와 실제로 저장된 중요 선택 중 필요한 사실만 사용합니다. 백엔드가 대표 활동 기록 4~6개와 중요 선택 최대 2개를 규칙으로 선별하고, 작가가 정한 직업별 서사 기준과 함께 Gemini에 전달합니다. 프롬프트는 **역할·안전 규칙(System), 이번 회차 사실(Context), 편지 작성 요청(Task), 출력·검증 조건(Contract)**으로 책임을 나눕니다. AI가 새로운 플레이 사실이나 어린이의 심리·진로 진단을 만들어 내지 못하도록 결과를 검증합니다.

Final Project는 **생성형 AI 또는 AI Agent가 핵심 기능일 것**과, 제시된 다섯 기술 요소 중 **두 가지 이상을 포함할 것**을 각각 요구합니다. Gemini 개인화 엔딩 편지는 핵심 기능이며, LUMIA가 선택한 두 기술 요소는 **자동화 워크플로우**와 **Long-term Memory**입니다. Gemini API 사용 자체를 두 기술 요소 중 하나로 세지 않습니다.

- **Long-term Memory:** 현재 회차의 활동 횟수와 중요 선택을 여러 주차·로그인 세션에 걸쳐 저장하고, 52주 종료 시 다시 읽어 실제 편지 입력에 사용합니다. 별도의 AI 메모리 서비스나 매주 LLM 요약을 두는 방식은 아닙니다.
- **자동화 워크플로우:** 규칙 기반 직업 확정, 회차 기록 선별, Gemini 생성, 응답 검증·재시도, 실패 시 사전 검수한 대체 편지, 준비 결과 저장, 엔딩 표시와 회차 확정을 연결합니다. 준비된 편지는 재접속·재시도 때 다시 생성하지 않습니다.

별도 AI Agent는 제출 버전에 넣지 않습니다. 엔딩의 처리 순서는 규칙으로 고정할 수 있으므로 자율적인 도구 선택보다 자동화 워크플로우가 재현성·안전성·검증 측면에서 적합합니다. Agent는 제출 후 부모/보호자 피드백을 고도화할 때 여러 회차·통계 조회 도구를 선택하는 기능으로 검토할 수 있습니다.

실제 구현·화면·실패 테스트를 통한 증명은 WBS 10.1.4의 코드와 실행 결과로 확인합니다.

### 4.2 Final Project 제출 후 확장

다음 항목은 현재 제출판의 핵심 동작을 완성한 뒤 확장합니다.

1. **관리자 기능 강화** — asset 자원 등록·교체, 대화 내용 변경, 캐릭터·펫 추가/관리 등 콘텐츠 CMS 기능
2. **UI 개선** — 기능 중심 UI를 고품질 디자인 버튼·창·인터랙션으로 교체
3. **사운드 개선** — 장소·상황·이벤트·성공/실패 결과에 맞춘 BGM/SFX 세분화
4. **부모/보호자와의 대화 연결** — 향후 운영 콘솔에서 여러 회차에 걸쳐 달라지는 아이의 관심과 선택을 조심스럽게 정리한 AI 보고서를 조회하고, 보호자가 대화를 시작할 단서를 제공하는 방향을 검토합니다. 보호자에게 제공할 화면·권한·내용 범위는 별도 설계하며 아이의 마음이나 성격을 단정하지 않습니다.
5. **미니게임 품질 개선** — 미니게임의 조작감·연출·피드백을 대폭 다듬고, 게임 전체의 세계관과 시각적 톤앤매너에 더욱 일관되게 맞춥니다.
6. **앱 전환 검토** — 현재 웹 기반 게임을 앱으로 확장하거나 전환하는 방안을 검토합니다. 플랫폼과 배포 방식은 후속 기획에서 결정합니다.
7. **인물·공간 확장** — 등장인물과 공간을 추가하고, 주인공 캐릭터에 따라 만나는 관계와 사건을 다양화하여 서로 다른 플레이 경험을 강화합니다.

이 항목들은 Final Project 제출 완료 조건을 위해 구현하지 않으며, 제출 버전의 구현·검증 일정에 포함하지 않습니다.

### 6.1 협업 방식과 실제 운영

팀은 [GitHub Project 애자일 보드](https://github.com/users/smong2/projects/2)를 공동 작업판으로 사용했습니다. WBS 이슈마다 담당자와 목표 일정을 두고, `Backlog`·`진행중`·`작업완료` 뷰를 통해 역할 배분뿐 아니라 실제 진행 현황과 작업 처리 내용을 공유했습니다. 예를 들어 [WBS 1.2 협업·인계 관리](https://github.com/smong2/codyssey_final/issues/47)는 [역할별 산출물·검수 기준](https://github.com/smong2/codyssey_final/issues/48)과 [의존 관계·일정 운영](https://github.com/smong2/codyssey_final/issues/49)으로 나누어 관리했습니다. 매일 회의에서 막힌 일과 다음 인계를 논의하고, 이슈·문서·Git 변경 이력을 연결해 결정을 확인할 수 있게 했습니다.

약 3주간의 기획에서는 사용자 문제와 세계관, 52주 경험, 영역 간 연결을 반복해서 검토했습니다. 세부 기능과 우선순위는 조정했지만 **어린이가 관계와 선택을 경험하는 게임**이라는 핵심 방향을 유지하며 구현까지 이어 갔습니다. `story/`·`asset/`·`engine/`·`backend/`로 주 작업 디렉터리를 나누어 병렬 작업의 간섭을 줄이고, 콘텐츠 ID·화면 흐름·API/데이터 계약은 공통 문서와 담당자 간 인계로 맞췄습니다. 상세 운영 기준은 [팀 역할과 협업 경계](05_TEAM_ROLES.md)에 정리했습니다.
