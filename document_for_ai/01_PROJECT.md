# 프로젝트 개요·환경

## 제품 정의

LUMIA는 약 9~11세 어린이가 룬 학원 **아르카디아**의 학생이 되어 친구와 관계를 맺고, 사건을 탐색하며, 자신의 선택이 세계에 남기는 변화를 경험하는 **웹 기반 판타지 생활 어드벤처 게임**이다. 10대 학생 캐릭터 32명이 설정되어 있다. 목표 경험은 `사건 발견 → 관찰·경청·탐색 → 선택 → 인물·룬·환경의 반응 → 마이룸에서 돌아보기`이다.

## 변하지 않는 설계 원칙

- 재미와 몰입을 앞세운다. 교육적 메시지나 도덕적 정답을 설명·채점하는 게임이 아니다.
- 선택은 `착함/나쁨`이나 성격 점수 대신 대화, 관계, 룬, 환경의 변화로 표현한다.
- 실패는 종료·벌점이 아니라 새 정보, 힌트 또는 다른 방법을 얻는 과정이다.
- 어린이의 개인적인 돌아보기는 안전한 맥락에 둔다. 보호자 경험은 감시·평가가 아니라 대화의 계기를 지향하며, 개인 기록 원문 공개를 전제하지 않는다.

## 제품·기술 경계

- 데스크톱·모바일에서 읽기·선택·조작 가능한 웹 게임을 지향한다.
- 생활 화면과 직접 탐험 화면은 **같은 아르카디아 장소**를 서로 다른 방식으로 표현한다. 별개의 세계나 단계형 맵으로 단정하지 않는다.
- 콘텐츠에는 안정적인 ID와 교체 가능한 데이터·이미지 연결을 지향한다.
- 기술 스택은 게임 클라이언트 **Phaser 3 + JavaScript/Node.js/Vite**, 프론트 배포 **Vercel**, API **Python + FastAPI / Render**, 인증 **Firebase Authentication Email/Password + 이메일 인증**, DB **Cloud Firestore**, 생성형 AI **Gemini API**로 확정했다. Gemini 기본 모델은 `gemini-3.8-flash`이며 환경변수로 교체한다. 실제 서비스 URL·Firebase 프로젝트 값과 세부 데이터/API 계약은 배포·구현 단계에서 확정한다.
- 계정은 **게스트 플레이 없이 Email/Password 가입 → 이메일 인증 → 게임 이용**의 단일 흐름을 사용한다. 가입 시 이메일 외 이름·나이·성별·전화번호 같은 추가 개인정보는 받지 않으며 개인정보 수집·이용 동의 시각과 버전만 계정 메타에 기록한다. Final Project 계정 관리에는 이메일 표시, 로그인 상태에서 현재 비밀번호 재인증을 통한 직접 변경, 비밀번호 분실 시 Firebase 재설정 메일, 로그아웃, `다른 기기에서 모두 로그아웃`, 계정 탈퇴가 포함된다. 다른 기기 로그아웃은 세션 폐기 후 현재 기기 즉시 재인증과 보호 API의 revocation 검증을 요구한다. 이메일 변경·계정 간 데이터 이전은 제공하지 않는다. 탈퇴하면 해당 UID의 세이브·Global Meta·엔딩 편지 등 Firestore 사용자 데이터와 Firebase Auth 계정을 모두 삭제하고 복구하지 않는다.
- Final Project의 관리자는 **LUMIA 제작·운영팀**이다. 관리자 계정은 최대 **3개**까지 운영하며, 일반 게임과 다른 관리자 주소에서 승인된 운영자 계정으로 로그인해 전체 사용자 목록·개별 플레이 기록·집계 통계를 조회하고, 반복 성장 콘텐츠의 5개 보이는 성장 스탯 보상 배율을 `0.5~1.0` 범위에서 스탯별로 조정할 수 있다. 통계는 최소 `일 / 주 / 월` 필터를 제공하고 월별 집계를 필수로 한다. 일반 사용자 계정은 관리자 권한이 없으면 접근할 수 없으며, 사용자별 세이브·스탯·해금을 직접 수정하거나 스토리 콘텐츠를 CRUD하는 기능은 제공하지 않는다. 핵심 이미지/asset 교체, 대화 수정, 캐릭터·펫 추가 같은 CMS 기능은 제출 후 확장으로 둔다. 관리자 로그인 성공/실패와 운영 값 변경은 감사로그로 남긴다. Gemini API Key와 Firebase Admin 자격 증명은 관리자 UI에서 다루지 않고 서버 환경변수로만 관리한다.
- 이 문서는 제품 방향의 요약이다. 구현 여부·현재 기술 환경을 묻는 작업에서는 실제 코드와 설정 파일을 직접 확인한다.

현재 `engine/`의 실행형 UI 시안은 동봉 Phaser 3와 Node.js 정적 서버를 사용하며 `node engine/server.mjs` → `http://127.0.0.1:4173/`로 확인한다. 7종 미니게임·일정·달력·로컬 저장·모험 이동 및 충돌·입학 연결 프레임이 있으며 Vite/운영 API·Firebase·Gemini 연동 완료를 뜻하지 않는다. 최신 기술 스택과 AI 엔딩 기획은 위 기준을 유지하며 실제 연결 상태와 구분한다. 세부 범위는 [엔진 README](../engine/README.md)를 따른다.

## Final Project 미션 경계

AI 엔딩은 현재 `engine/`에 직업 결과와 3개 편지 섹션을 보여 주는 프레임·예시 편지·조회 adapter 연결 지점이 있다. 예시는 실제 판정/AI 결과가 아니며 저장·해금에 반영되지 않는다. 백엔드 코드/endpoint 계약이 없어 실제 AI 호출·안전 검증·엔딩 저장은 미연결이다. [엔진 프레임 안내](../engine/ENDING_FRAME.md)를 확인한다.

[최종 과제 요구사항](../document/08_REQUEST.md)의 필수 기능·제약 사항은 생성형 AI **또는** AI Agent를 서비스의 핵심 기능으로 요구하며, 지정된 기술 요소 다섯 가지 중 두 가지 이상, 외부 접근 가능한 배포, 실제 사용자 최소 5명의 테스트와 피드백 반영이 필요하다. 기획서·요구 명세서·아키텍처·발표 자료와 GitHub 기록도 산출물이다. LUMIA의 **AI 핵심 기능은 52주 종료 후 규칙 엔진이 확정한 미래 직업과 실제 플레이 기록을 바탕으로 Gemini가 개인화 엔딩 편지를 작성하는 기능**으로 확정했다. AI는 직업 자체를 판정하지 않는다. Final Project 기술 요소는 **Long-term Memory + 자동화 워크플로우** 두 가지를 선택하고 별도 AI Agent는 제출판에서 사용하지 않는다. Long-term Memory는 일반 세이브를 뜻하지 않으며, 현재 회차에서 여러 주차·세션에 걸쳐 활동 결과와 중요 선택을 누적한 `Long-term Play Memory`를 52주 종료 시 다시 읽어 대표 기록과 중요 선택을 `AI Memory Context`로 구성하고 실제 Gemini 입력에 사용하는 구조다. 다음 회차 편지에는 이전 회차 기억을 자동으로 섞지 않으며, 최종 편지와 사용한 대표 기억은 회차별 Ending Record에 보관한다. 자동화 워크플로우는 `엔딩 판정 → 장기 기억 로드 → 기록 선별 → Gemini 호출 → 검증/재시도/fallback → 저장/표시 → 메타 반영`을 자동 연결한다. 실제 인정 근거는 구현 코드·화면·저장/재접속·실패/fallback 테스트로 검증한다. 상세 기준은 [AI 핵심 기능](../document/09_AI_ENDING_LETTER.md), [기술 스택](../document/10_TECH_STACK.md), [요구 명세](../document/12_REQUIREMENTS_ARCHITECTURE.md)를 확인한다.

제출 범위는 [Final Project 기획서](../document/11_PROJECT_PLAN.md)의 **Must / Should / Post-Submission** 표로 고정한다. Must는 52주 핵심 게임·계정/저장·AI 엔딩·관리자 최소 운영 기능·배포·5명 사용자 검증과 필수 제출 근거이며, 별도 AI Agent와 asset/콘텐츠 CMS·고도화된 부모 피드백은 제출 후 범위다. AI 프롬프트 기획은 `System Prompt / Task Context / Task Prompt / Output Contract` 네 계층의 책임을 고정하고, 기억은 Firestore의 구조화된 Long-term Play Memory를 백엔드가 직접 조회·선별한다. 별도 RAG·벡터 검색·외부 웹 검색은 제출판에서 사용하지 않는다.
