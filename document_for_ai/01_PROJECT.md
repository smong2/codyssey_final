# 프로젝트 개요·환경

## 제품 정의

LUMIA는 약 9~11세 어린이가 룬 학원 **아르카디아**의 학생이 되어 친구와 관계를 맺고, 사건을 탐색하며, 자신의 선택이 세계에 남기는 변화를 경험하는 **웹 기반 판타지 생활 어드벤처 게임**이다. 10대 학생 캐릭터 32명이 설정되어 있다. 목표 경험은 `사건 발견 → 관찰·경청·탐색 → 선택 → 인물·룬·환경의 반응 → 마이룸에서 돌아보기`이다.

프로젝트는 어린이가 타인의 마음을 이해하고 배려·협력하는 경험을 어떻게 얻을 수 있는지, 보호자가 아이와 대화를 시작할 단서를 어떻게 얻을 수 있는지에 대한 문제의식에서 출발했다. 미디어에서 접한 어린이의 사회적 관계에 대한 우려가 계기이지 모든 어린이를 진단하는 주장은 아니다. 아르카디아에서는 서로 다른 성격과 배경의 학생 32명 중 주인공을 골라 52주 동안 여러 인물·사건·선택을 만난다. 아이가 무엇에 마음을 움직이는지 스스로 생각하도록 돕고, 누적된 경험을 개인화 엔딩으로 되돌려준다.

## 변하지 않는 설계 원칙

- 재미와 몰입을 앞세운다. 교육적 메시지나 도덕적 정답을 설명·채점하는 게임이 아니다.
- 선택은 `착함/나쁨`이나 성격 점수 대신 대화, 관계, 룬, 환경의 변화로 표현한다.
- 실패는 종료·벌점이 아니라 새 정보, 힌트 또는 다른 방법을 얻는 과정이다.
- 어린이의 개인적인 돌아보기는 안전한 맥락에 둔다. 보호자 경험은 감시·평가가 아니라 대화의 계기를 지향하며, 개인 기록 원문 공개를 전제하지 않는다.

## 제품·기술 경계

- 데스크톱·모바일에서 읽기·선택·조작 가능한 웹 게임을 지향한다.
- 생활 화면과 직접 탐험 화면은 **같은 아르카디아 장소**를 서로 다른 방식으로 표현한다. 별개의 세계나 단계형 맵으로 단정하지 않는다.
- 콘텐츠에는 안정적인 ID와 교체 가능한 데이터·이미지 연결을 지향한다.
- 기술 스택은 게임 클라이언트 **Phaser 3 + JavaScript/Node.js/Vite**, 게임 프론트 배포 **Vercel**, 관리자 콘솔 **Next.js + Tailwind CSS / Vercel**, API **Python + FastAPI / Render**, 인증 **Firebase Authentication Email/Password + 이메일 인증**, DB **Cloud Firestore + 플레이어 브라우저 로컬 SQLite**, 생성형 AI **Gemini API**로 확정했다. Phaser 3는 기존 데모 재사용보다 브라우저 우선 2D 구조, WebGL/Canvas 렌더링, JavaScript 웹 생태계와의 직접 결합, 범용 3D 엔진보다 단순한 빌드·배포 경계를 이유로 선택한다. 관리자 콘솔은 표·검색·통계·설정 중심의 DOM 업무 UI이므로 게임 Canvas와 분리해 Next.js/React 구조와 Tailwind CSS를 사용한다. Firestore는 사용자별 확정 세이브·메타·현재 회차 기억·엔딩과 관리자 중앙 통계·운영 배율·감사로그를 담당한다. SQLite는 플레이어 기기의 마스터·화면 캐시와 임시 상태에 사용하며 관리자 데이터 원본이 아니다. 웹 구현 방식은 SQLite WASM/OPFS를 검토하고 브라우저 호환·대체 경로를 검증한다. Gemini 기본 모델은 `gemini-3.8-flash`이며 환경변수로 교체한다. 운영 Firebase 프로젝트는 `codyssey-final`, 게임 웹은 `https://lumia-web-six.vercel.app/`, 관리자 콘솔은 `https://codyssey-final-ujhz.vercel.app/`, API는 `https://lumia-api-pcxd.onrender.com/`이다. 운영 환경에서 52주 테스트 fixture를 이용한 엔딩 진입 → 서버 직업 결정 → Gemini 개인화 편지 → 엔딩 표시 → 회차 완료 E2E까지 성공 확인했다.
- 계정은 **게스트 플레이 없이 Email/Password 가입 → 이메일 인증 → 게임 이용**의 단일 흐름을 사용한다. 가입 시 이메일 외 이름·나이·성별·전화번호 같은 추가 개인정보는 받지 않으며 개인정보 수집·이용 동의 시각과 버전만 계정 메타에 기록한다. Final Project 계정 관리에는 이메일 표시, 로그인 상태에서 현재 비밀번호 재인증을 통한 직접 변경, 비밀번호 분실 시 Firebase 재설정 메일, 로그아웃, `다른 기기에서 모두 로그아웃`, 계정 탈퇴가 포함된다. 다른 기기 로그아웃은 세션 폐기 후 현재 기기 즉시 재인증과 보호 API의 revocation 검증을 요구한다. 이메일 변경·계정 간 데이터 이전은 제공하지 않는다. 탈퇴하면 해당 UID의 Firestore 사용자 데이터와 Firebase Auth 계정을 모두 삭제하고 복구하지 않는다. 현재 기기의 로컬 캐시도 지우고 다른 기기의 캐시는 이후 인증·동기화 시 무효화한다.
- Final Project의 관리자는 **LUMIA 제작·운영팀**이다. 관리자 계정은 최대 **3개**까지 운영하며, 일반 게임과 다른 관리자 주소에서 승인된 운영자 계정으로 로그인해 전체 사용자 목록·개별 플레이 기록·집계 통계를 조회하고, 반복 성장 콘텐츠의 5개 보이는 성장 스탯 보상 배율을 `0.5~1.0` 범위에서 스탯별로 조정할 수 있다. 통계는 최소 `일 / 주 / 월` 필터를 제공하고 월별 집계를 필수로 한다. 일반 사용자 계정은 관리자 권한이 없으면 접근할 수 없으며, 사용자별 세이브·스탯·해금을 직접 수정하거나 스토리 콘텐츠를 CRUD하는 기능은 제공하지 않는다. 핵심 이미지/asset 교체, 대화 수정, 캐릭터·펫 추가 같은 CMS 기능은 제출 후 확장으로 둔다. 관리자 로그인 성공/실패와 운영 값 변경은 감사로그로 남긴다. Gemini API Key와 Firebase Admin 자격 증명은 관리자 UI에서 다루지 않고 서버 환경변수로만 관리한다.
- 이 문서는 제품 방향의 요약이다. 구현 여부·현재 기술 환경을 묻는 작업에서는 실제 코드와 설정 파일을 직접 확인한다.

`engine/`에는 Phaser 3 실행형 UI 시안과 통합 작업이 함께 있다. 독립 데모나 로컬 시안의 동작을 운영 서비스 전체 완료로 간주하지 않는다. 최신 연결·검증 상태는 [게임 콘텐츠 AI 요약](03_GAME_CONTENT.md), [엔진 README](../engine/README.md), 실제 코드와 테스트 결과를 확인한다.

## Final Project 미션 경계

AI 엔딩에는 엔진 표시 프레임과 백엔드의 직업 판정·편지 준비·검증·저장 흐름이 각각 작업되어 있다. 코드·로컬 회귀 검증과 실제 Gemini 호출·운영 브라우저 종단 검증은 별개이므로 구현 완료를 이 요약만으로 판단하지 않는다. 최신 상태는 [게임 콘텐츠 AI 요약](03_GAME_CONTENT.md), [엔진 프레임 안내](../engine/ENDING_FRAME.md), 실제 코드와 테스트 결과를 확인한다.

[최종 과제 요구사항](../document/08_REQUEST.md)은 생성형 AI **또는** AI Agent를 서비스의 핵심 기능으로 요구하며, 지정된 기술 요소 다섯 가지 중 두 가지 이상, 외부 접근 가능한 배포, 실제 사용자 최소 5명의 테스트와 피드백 반영이 필요하다. 기획서·요구 명세서·아키텍처·발표 자료와 GitHub 기록도 산출물이다. LUMIA의 **AI 핵심 기능은 52주 종료 후 규칙 엔진이 확정한 미래 직업과 현재 회차의 실제 스탯·활동·선택을 바탕으로 Gemini가 개인화 엔딩 편지를 작성하는 기능**이다. AI는 직업 자체를 판정하지 않는다. 프롬프트는 System / Context / Task / Contract 네 계층으로 역할을 나누고, 백엔드가 현재 회차 저장값에서 대표 활동과 실제 중요 선택만 규칙으로 선별한다. 자동화 워크플로우는 `직업 확정 → 입력 구성 → Gemini 호출 → 검증/재시도/대체 편지 → 준비 저장 → 표시 → 회차 확정`을 연결하며, 준비된 편지는 재접속 때 다시 생성하지 않는다. 필수 기술 요소는 **자동화 워크플로우 + Long-term Memory** 두 가지를 선택한다. Long-term Memory는 별도 AI 메모리 서비스가 아니라 여러 주차·세션에 걸쳐 유지된 현재 회차 활동·중요 선택을 엔딩 시 다시 읽어 실제 Gemini 입력에 사용하는 Long-term Play Memory다. 기술 요소의 실제 충족 여부는 코드와 실행 결과로 검증한다. 별도 AI Agent·RAG·멀티모달 AI도 현재 제출판에서 사용하지 않는다. 상세 기준은 [AI 핵심 기능](../document/09_AI_ENDING_LETTER.md), [기술 스택](../document/10_TECH_STACK.md), [요구 명세](../document/12_REQUIREMENTS_ARCHITECTURE.md)를 확인한다.

제출 범위는 [Final Project 기획서](../document/11_PROJECT_PLAN.md)의 **Must / Should / Post-Submission** 표로 고정한다. Must는 52주 핵심 게임(5개 미니게임과 `요정의 거래` 포함)·계정/저장·AI 엔딩 및 생성물 안내·관리자 최소 운영 기능·배포·5명 사용자 검증과 필수 제출 근거이며, 별도 AI Agent와 asset/콘텐츠 CMS·보호자 대화 단서를 위한 AI 활동 보고서는 제출 후 범위다. 미니게임 품질과 게임 전체 톤앤매너 개선, 등장인물·공간 추가를 통한 주인공별 경험 확대도 제출 후 확장한다. 웹 게임의 앱 전환은 검토 방향이며 플랫폼과 배포 방식은 확정하지 않았다. 향후 운영 콘솔에서 해당 보고서를 조회하는 방향을 검토하되 보호자 제공 화면·권한·내용은 별도 설계하며 아이의 마음이나 성격을 단정하지 않는다. 관리자 AI 키 등록·교체 화면은 후속 범위에도 넣지 않는다. Gemini API 키와 Firebase Admin 자격 증명은 배포 환경의 비밀 변수와 권한으로 관리한다. AI 프롬프트 기획은 `System Prompt / Task Context / Task Prompt / Output Contract` 네 계층의 책임을 고정하고, Long-term Play Memory의 원본은 Firestore의 현재 회차 저장값이며 백엔드가 직접 조회·선별한다. 별도 RAG·벡터 검색·외부 웹 검색은 제출판에서 사용하지 않는다.

팀은 [GitHub Project 애자일 보드](https://github.com/users/smong2/projects/2)를 공동 작업판으로 사용해 WBS 담당자·일정·진행 현황과 처리 내용을 공유했다. 약 3주간 기획과 매일 회의를 통해 핵심 방향을 유지하며 세부 우선순위를 조정했고, 역할별 디렉터리와 공통 인계 문서로 병렬 작업을 연결했다. 실제 협업 방식은 [팀 역할](../document/05_TEAM_ROLES.md)과 [기획서](../document/11_PROJECT_PLAN.md)를 확인한다.
